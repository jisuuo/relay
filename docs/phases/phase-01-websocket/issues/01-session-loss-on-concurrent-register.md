# ISSUE-01. 동시 접속 시 세션이 예외 없이 사라짐

- 날짜: 2026-10-24
- 과제: P1-1 WebSocket 연결과 종료
- 관련: [개념 노트](../../../learning/session-store-concurrency.md), `SessionRegistry`, `SessionRegistryTest`

## 1. 문제 발생

- 상황: 연결 시 세션을 저장소에 등록하고 종료 시 제거한다. 처음 저장소는 `HashSet`이었다.
- 재현: `SessionRegistryTest`에서 100개 스레드가 `CountDownLatch` 출발 신호로 동시에 출발해 스레드마다 세션 100개를 등록 → 기대 `size == 10000`.
- 결과 (실제 실행): **10회 모두 실패.** 메시지를 확인한 6회는 10000개 중 **6611~8546개만 남음**(1,454~3,389개 유실).
- 특징: **예외도 로그도 없다.** 서버는 정상으로 보이지만, 사라진 사용자는 연결된 채로 메시지를 받지 못한다. 접속자 수도 실제보다 적게 집계된다.

## 2. 원인 분석

- Tomcat은 연결 이벤트(`afterConnectionEstablished`)를 스레드 풀의 여러 스레드로 동시에 처리한다. 모든 스레드가 **같은 저장소 객체 하나**에 쓴다.
- `HashSet`은 스레드 안전하지 않다. `add()` 한 번도 내부에서는 버킷 연결, `size++`, resize(원소 수가 `capacity × 0.75`를 넘으면 2배 배열로 옮겨 담기) 같은 **여러 단계**로 실행된다.
- 두 스레드가 이 단계 사이에 끼어들면(경쟁 조건) 한쪽 결과가 덮어써진다. resize 도중 다른 스레드가 **기존 배열**에 넣은 원소는 참조가 새 배열로 바뀌면서 버려진다.

  | 시점 | 스레드 1 | 스레드 2 | count |
  |---|---|---|---|
  | t1 | 읽기 → 0 | | 0 |
  | t2 | | 읽기 → 0 | 0 |
  | t3 | 쓰기 → 1 | | 1 |
  | t4 | | 쓰기 → 1 | **1** (기대값 2) |

- 확인하지 못한 것: 유실 중 resize 때문인 것과 버킷 연결·`size` 경합 때문인 것이 각각 몇 건인지는 측정하지 않았다.

## 3. 해결 방안과 해결

### 검토한 방안

| 방안 | 방식 | 판단 |
|---|---|---|
| `Collections.synchronizedSet(new HashSet<>())` | Set 전체에 락 하나 | 안전하지만 수천 연결이 한 줄로 대기함. 반복할 때는 직접 락을 잡아야 함 |
| **`ConcurrentHashMap.newKeySet()`** | 버킷 단위 락, 빈 버킷은 CAS | 서로 다른 버킷을 건드리는 스레드는 기다리지 않고 동시에 진행됨. 반복 중에 수정돼도 예외 없음 |
| `CopyOnWriteArraySet` | 쓰기마다 배열 전체 복사 | 연결·종료가 잦아 부적합함 |

### 해결

- 저장소를 `ConcurrentHashMap.newKeySet()`으로 교체했다.
- 결과 (실제 실행): 같은 테스트 **10회 모두 통과**(`size == 10000`). `./gradlew test` 전체 4개 통과.

### 남은 것

- `ConcurrentHashMap` 반복은 weakly consistent다. 브로드캐스트 도중 입장·퇴장한 세션이 이번 반복에 보일 수도, 안 보일 수도 있다 → P1-4에서 검토한다.
- 이런 버그는 운영 환경에서 예외 없이 사용자 증상으로만 드러난다. 그래서 실패하도록 설계한 테스트로 미리 잡고, 운영에서는 접속자 수 메트릭(P1-6)이 실제 연결 수와 어긋나는지로 간접 감지한다.
