# ISSUE-03. 빈 방 삭제와 JOIN이 겹치면 삭제된 방에 들어감

- 날짜: 2026-10-24
- 과제: P1-3 채팅방 및 세션 관리
- 관련: [ADR-0008](../../../adr/0008-room-registry-global-lock.md), `RoomRegistry`, `RoomRegistryConcurrencyTest`

## 1. 문제 발생

- 문제 문장 (정의 단계, 내 표현): "마지막 1명 LEAVE로 빈 방 삭제 직전 JOIN이 방을 쥐면 유실"
- 재현: `RoomRegistryConcurrencyTest`. 시도마다 방 1,000개에 세션을 1명씩 넣고, 두 스레드가 `CountDownLatch`로 동시에 출발한다. 한 스레드는 모든 방에서 그 1명을 `LEAVE`(또는 끊김 `removeSession`)하고, 다른 스레드는 같은 방들에 새 세션을 `JOIN`한다. 끝나면 불변식 ①·②를 양방향으로 검사한다. 이를 200번 반복한다.
- 결과 (실제 실행, 방어 없는 `ConcurrentHashMap` 구현): **11회 실행 모두 두 테스트 실패.** 테스트별로 나눠 확인한 5회에서 위반이 생긴 시도는 200회 중 `LEAVE` 경로 22~36회, 끊김 경로 20~45회.
- 위반은 모두 "세션 목록에는 방 A가 있는데 맵에 방 A(또는 그 안의 세션)가 없음"이었다. **예외는 없었다.**
- 사용자 증상: T는 입장에 성공했다고 알지만, 이후 새로 만들어진 방 A로 오는 메시지를 받지 못한다.

## 2. 원인 분석

| 시점 | 스레드 1 (S `LEAVE A`) | 스레드 2 (T `JOIN A`) | `rooms` 맵 | 스레드 2가 쥔 집합 |
|---|---|---|---|---|
| 1 | 방 A에서 S 제거 | | `{A → {}}` | — |
| 2 | "비었네" 확인 | | `{A → {}}` | — |
| 3 | | 방 A 집합을 꺼내 쥠 | `{A → {}}` | `{}` |
| 4 | 맵에서 방 A 삭제 | | `{}` | `{}` (맵과 연결 끊김) |
| 5 | | 쥔 집합에 T 추가, T의 방 목록에 A 추가 | `{}` | `{T}` |

- `ConcurrentHashMap`의 `get`·`remove`·`add` 각각은 안전하지만, "빈 방 확인 → 삭제"와 "방 찾기 → 추가"처럼 **여러 단계를 묶은 동작**은 안전하지 않다.
- 끊김 처리도 같은 "빈 방 확인 → 삭제" 2단계를 가져서 같은 문제가 생긴다. 문제는 `LEAVE`·끊김이 아니라 "빈 방 삭제" 동작 자체에 있다.
- 검사는 양방향이어야 한다. 이 경쟁에서는 맵에 방이 없어 "방 → 세션" 방향으로는 검사할 것이 없고, "세션 → 방" 방향에서만 드러난다. 실제 위반도 모두 이 방향이었다.

## 3. 해결 방안과 해결

### 검토한 방안

| 방안 | 판단 |
|---|---|
| 방마다 락 (방 찾기는 락 밖) | 처음 생각. 락을 기다리는 동안 방이 삭제되면 락을 잡은 뒤 삭제된 방에 추가함 → 해결 안 됨 |
| **전체 락 하나** | 방 찾기부터 두 매핑 갱신까지 락 안. 서로 다른 방도 줄을 섬 |
| 방마다 락 + 재확인 | 해결되지만 "같은 객체인가" 비교·재시도·락 안 삭제 규칙이 필요 |

### 해결

- `RoomRegistry`의 모든 메서드를 `synchronized`(전체 락 하나)로 감쌌다 (ADR-0008).
- 결과 (실제 실행): 같은 테스트 **5회 모두 통과**. `./gradlew test` 전체 42개 통과.

### 남은 것

- 통과는 "이 조건에서 겹침을 찾지 못했다"는 뜻이지 안전 증명은 아니다. 안전하다는 근거는 모든 접근이 같은 락 안에 있다는 추론이다.
- 전체 락 대기가 병목인지는 P1-7 k6 측정에서 확인한다. 병목이면 방마다 락 + 재확인으로 바꾼다.
