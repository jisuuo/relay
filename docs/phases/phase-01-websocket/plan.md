# Phase 01. 최소 실시간 채팅 서버 — 계획

- 상태: 진행 중
- 시작일: 2026-10-24
- 선행 Phase: P0

## 학습 목표

- WebSocket 연결의 수명주기(handshake → message → close)와 정상·비정상 종료의 차이를 이해한다.
- 방 관리와 브로드캐스트를 직접 구현하면서 생기는 문제(동시 수정, 끊긴 세션, 동시 전송)를 테스트로 재현하고 해결한다.
- 이후 Phase의 비교 기준이 될 기준 성능을 측정한다.

## 문제 정의

HTTP 요청/응답만으로는 서버가 클라이언트에게 먼저 메시지를 보낼 수 없다. polling은 주기에 따라 부하와 지연 중 하나를 포기해야 한다.
WebSocket은 연결과 frame 전달만 제공하므로, 채팅방 단위의 전달(방 관리·브로드캐스트·격리)은 애플리케이션이 책임져야 한다.

## 범위 / 비범위

**범위**

- WebSocket 연결과 종료 (정상 close, 비정상 단절)
- JSON 메시지 모델 (입장·퇴장·전송)
- 채팅방 및 세션 관리 (방 → 세션 매핑)
- 같은 방 브로드캐스트, 다른 방 메시지 격리
- 잘못된 입력 처리
- 최소 관측: Micrometer 커스텀 메트릭 (활성 세션 수, 메시지 처리량) — [CHG-002](../../changes/002-early-minimal-observability.md)
- k6 기준 성능 측정 — [CHG-001](../../changes/001-move-baseline-perf-to-phase1.md)
- (선택) 느린 소비자 실험

**비범위**

- 메시지 저장·조회 (P2)
- 인증·인가, WebSocket 보안 (P9)
- 서버 간 메시지 전달 (P6)
- STOMP, SockJS ([ADR-0004](../../adr/0004-raw-websocket-over-stomp.md))
- 클라이언트 UI (테스트 클라이언트와 k6로 검증)

## 시작 결정

메시징 방식은 Raw WebSocket(`WebSocketHandler`)으로 시작한다 — [ADR-0004](../../adr/0004-raw-websocket-over-stomp.md).

## 원인 가설 (구현하며 확인할 것)

- 방 → 세션 매핑을 일반 컬렉션으로 두면, 브로드캐스트 중 입장·퇴장이 일어날 때 동시 수정 문제가 생긴다.
- 비정상 단절 시 close frame이 오지 않으므로, 서버가 단절을 곧바로 알지 못하고 끊긴 세션이 매핑에 남는다.
- 같은 세션에 여러 스레드가 동시에 `send`하면 실패한다.
- 브로드캐스트를 순차 반복으로 하면, 느린 세션 하나가 같은 방 전체의 전달을 지연시킨다.

> 고민 결과: 연결 시 세션 등록, 종료 시 제거. 비정상 단절은 서버 주도 WebSocket ping/pong으로 감지한다 — [ADR-0005](../../adr/0005-websocket-ping-pong-heartbeat.md).
> 설계 메모: 세션 저장소는 `ConcurrentHashMap.newKeySet()` — [개념 노트](../../learning/session-store-concurrency.md).
>
> 설계 확정:
> - 구성: `WebSocketHandler` 구현체(연결 시 등록, 종료 시 제거), 세션 저장소, 엔드포인트 `/ws`
> - 테스트 ① 동시 등록(단위): 출발 신호(`CountDownLatch`)로 N개 스레드가 동시에 add → `size == N`. `HashSet`으로 먼저 실패를 재현한 뒤 교체
> - 테스트 ② 연결 시 등록(통합): 실제 WebSocket 클라이언트 연결 → 저장소에 세션 1개
> - 테스트 ③ 정상 종료 시 제거(통합): 클라이언트 close → 저장소에서 제거
> - heartbeat(ADR-0005)는 비정상 종료와 함께 P1-5에서 다룬다.
>
> 구현·검증 결과 (2026-10-24, 실제 실행):
> - ① `HashSet`: 10회 모두 실패, 확인한 6회는 10000개 중 6611~8546개만 남음(예외 없음) → `ConcurrentHashMap.newKeySet()` 교체 후 10회 모두 통과
> - ②·③ 구현 전: handshake 404로 실패 → `ChatWebSocketHandler`·`WebSocketConfig` 구현 후 통과
> - `./gradlew test` 전체 4개 통과
>
> 정리 (2026-10-24):
> - 배운 것 (내 표현): "예외를 주지 않기 때문에 잃어버린 유실에 관해 알 수가 없습니다."
> - 보충: 동시성 버그는 로그·알림 없이 사용자 증상("가끔 메시지가 안 와요")으로만 드러나고, 부하 상황에서만 확률적으로 생겨 개발 환경에서 재현되지 않는다. 그래서 실패하도록 설계한 테스트로 미리 잡고, 운영에서는 접속자 수 메트릭(P1-6)과 실제 연결 수의 불일치로 간접 감지한다.
> - 남은 것: 비정상 단절 감지(heartbeat)는 P1-5로 이관.
> - 문제 기록: [ISSUE-01](issues/01-session-loss-on-concurrent-register.md)

### P1-2 JSON 메시지 모델
- [x] 1. 정의: 요구사항과 문제 정의
- [x] 2. 고민: 원인·해결책 직접 고민, 힌트, 대안 비교 → (필요 시) ADR
- [x] 3. 설계: 최소 설계와 테스트 시나리오 확정
- [x] 4. 구현·검증: 실패하는 테스트 → 구현 → 통과, 예상 vs 실제 비교
- [x] 5. 정리: 결과 분석, 회고 기록

> 메모: 메시지 종류(`JOIN`·`LEAVE`·`SEND`)와 필드(`roomId`, `content` 등)를 정한다.
>
> 정의 (2026-10-24):
> - 연결(`/ws` 접속)과 방 입장은 다른 일이다. 입장도 메시지의 한 종류다.
> - 한 세션이 여러 방에 동시에 참여할 수 있다(다중 방). 그래서 서버가 세션만 보고 대상 방을 정할 수 없고, `LEAVE`·`SEND`에도 `roomId`가 필요하다. 1세션 1방 모델과의 비교는 설계 단계에서 ADR로 남긴다.
> - 원칙: 서버가 이미 확실히 아는 것(누가 보냈는지 = 세션)은 메시지에서 받지 않고, 받아도 믿지 않는다. 클라이언트만 아는 것(어느 방에, 무엇을)은 메시지에 담는다.
>
> | type | 필드 | 서버가 확인할 것 (P1-3·4) |
> |---|---|---|
> | `JOIN` | `roomId` | 방 존재 여부(또는 생성) |
> | `LEAVE` | `roomId` | 그 방 멤버인지 |
> | `SEND` | `roomId`, `content` | 그 방 멤버인지 |
>
> - 타입마다 필요한 필드가 다르다 → "2. 고민"의 주제: 이를 Java로 어떻게 표현할 것인가.
> - 경계: P1-2는 메시지만 보고 알 수 있는 실패를 **판별**한다(① JSON 파싱 실패 ② 모르는 `type` ③ 필수 필드 누락). 서버 상태가 필요한 검사(비멤버의 `SEND` 등)는 P1-3·4, 판별된 실패에 대한 **대응**(에러 응답 형식, 연결 유지 여부)은 P1-5에서 다룬다.
>
> 고민 결과 (2026-10-24):
> - 처음 생각: 클래스 하나(`type`·`roomId`·`content`)로 받고 controller 단에서 검증.
> - 반례: 단일 클래스는 JOIN에 붙은 `content`도 통과시키고, "SEND일 때만 content 필수" 같은 조건부 검증을 if문으로 써야 하며, 새 타입의 처리 분기를 빠뜨려도 컴파일러가 알려 주지 않는다. Raw WebSocket(ADR-0004)에는 controller·`@Valid`가 없고, MVC에서도 검증은 controller 호출 전 바인딩 단계에서 일어난다.
> - 비교: A 단일 클래스 / **B 타입별 record + sealed interface (Jackson `@JsonTypeInfo`로 `type` 기준 역직렬화)** / C 봉투 `{type, payload}` (와이어 형식 변경, 현재 과함) → **B 채택**. 새 의존성 없음(Jackson 3.1.7 이미 포함).
> - 위치: 핸들러(입출력)와 분리된 파서가 `String` → `ClientMessage` 변환 중에 ①②③을 판별한다.
> - 열린 점: ③ 필수 필드 누락은 Jackson이 자동으로 걸러 주지 않을 것으로 예상(null 필드로 record 생성) → 설계 단계 테스트로 확인.
> - ADR 후보: 다중 방 vs 1세션 1방, 메시지 표현 방식(A/B/C).
>
> 설계 확정 (2026-10-24) — [ADR-0006](../../adr/0006-multi-room-per-session.md), [ADR-0007](../../adr/0007-typed-client-message-model.md):
> - 구성: `ClientMessage` sealed interface + `JoinMessage(roomId)`·`LeaveMessage(roomId)`·`SendMessage(roomId, content)` record, `String` → `ClientMessage` 파서. 실패는 파서가 하나의 예외 타입으로 감싸서 던진다(대응은 P1-5).
> - 검증 위치: 각 record의 compact constructor. `roomId`·`content`는 `null`·`""`·공백만 → 거절. `" 안녕 "`은 그대로 보존.
> - 모르는 필드(`sender`, `JOIN`의 `content` 등): 무시.
> - 범위: 파서와 단위 테스트까지. 핸들러에 연결해 메시지를 처리하는 일은 P1-3에서 한다.
> - 테스트 시나리오 (파서 단위 테스트):
>   1. `JOIN`·`LEAVE`·`SEND` 정상 → 해당 record와 필드 값
>   2. JSON 문법 오류 → 실패
>   3. 모르는 `type`, `type` 누락 → 실패
>   4. `roomId` 누락·`null`·`""`·공백만 (세 타입 각각) → 실패
>   5. `SEND`의 `content` 누락·`null`·`""`·공백만 → 실패
>   6. `content: " 안녕 "` → 공백 포함 그대로 보존
>   7. 모르는 필드 포함(`"sender":"bob"`, `JOIN`의 `content`) → 무시하고 성공
>   8. 파서 없이 `new SendMessage("A", null)` 직접 생성 → 예외
> - 확인할 예상 (실행 전): 생성자 검사가 없으면 Jackson이 `null`로 채워 record를 만든다 / 생성자 예외는 Jackson 예외로 감싸진다 / Jackson 3의 모르는 필드 기본 동작.
>
> 구현·검증 결과 (2026-10-24, 실제 실행):
> - 생성자 검사 없는 record: `ClientMessageParserTest` 27개 중 17개 실패 — 시나리오 4(12개)·5(4개)·8(1개) 전부. 필수 필드가 누락·`null`·`""`·공백만이어도 Jackson은 예외 없이 객체를 반환했고, `new SendMessage("A", null)`도 생성됐다 → 예상대로 Jackson은 필수 여부를 모른다.
> - 같은 실행에서 시나리오 7(모르는 필드)은 `JsonMapper.builder().build()` 기본값만으로 통과 → Jackson 3.1.7 기본값은 무시. 정책을 드러내려고 `FAIL_ON_UNKNOWN_PROPERTIES`를 명시적으로 끄도록 바꿨다.
> - compact constructor 검사 추가 후: 27개 모두 통과, `./gradlew test` 전체 31개 통과.
> - 예외 감싸기 (`SendMessage` content 누락으로 확인): `IllegalArgumentException` → Jackson `ValueInstantiationException` → 파서의 `InvalidMessageException`.
>
> 정리 (2026-10-24):
> - 배운 것 (내 표현): "요청이 들어오면 어디서 검사를 해야 하는지에 대한 책임을 아는 것", "sealed, record에 대해서도 알게 되었다"
> - 보충: 검사의 책임 위치는 "무엇을 봐야 알 수 있는가"로 정해진다.
>   - 메시지만 보면 아는 것 → 파서(JSON 문법·`type`) + record 생성자(필수 필드)
>   - 서버 상태를 봐야 아는 것(방 멤버인지) → P1-3·4
>   - 실패에 어떻게 대응할지 → P1-5
>   - 필수 필드 검사를 생성자에 둔 이유: 객체 밖의 한 경로(파서)에 두면 다른 경로로 우회할 수 있다. 생성자에 두면 "객체가 존재한다 = 유효하다"가 된다.
> - 개념 노트: [메시지 검사의 책임](../../learning/message-validation-responsibility.md)
> - 문제 기록: [ISSUE-02](issues/02-jackson-creates-message-without-required-fields.md)
> - 남은 것: 파서를 핸들러에 연결해 메시지를 처리하는 일은 P1-3, 실패 대응은 P1-5.

> 메모: 방 → 세션 매핑의 자료구조와, 입장·퇴장이 동시에 일어날 때의 안전성을 다룬다.
>
> 정의 진행 (2026-10-24):
> - 상태: 방 → {세션들}, 세션 → {방들} 두 매핑([ADR-0006](../../adr/0006-multi-room-per-session.md) 다중 방). 두 번째 매핑이 필요한 이유는 연결 끊김 정리다. 방 → {세션들}만 있으면 끊긴 세션을 찾으려고 전체 방을 훑어야 하고(방 10,000개 중 실제로 지우는 건 2개), 사용자는 보통 `LEAVE` 없이 연결을 끊으므로 이 정리가 주요 경로다.
> - 질문 1 (불변식), 내가 적은 문장:
>   - "방 A에 S가 있으면 S의 방 목록에도 A가 있다", "방 A에 S가 없으면 S의 방 목록에도 A가 없다" → 합치면 S ∈ 방 A의 세션들 ⇔ A ∈ S의 방들
>   - "빈 방은 존재하지 않는다"
>   - "끊긴 세션은 매핑에 없다"
> - 고쳐야 할 처음 생각: `LEAVE` 때 "할 일 없음", 끊김 때 "재연결 대비로 그대로 둠" → 두 생각 모두 위 불변식을 깨뜨린다. 끊긴 `WebSocketSession`은 다시 쓸 수 없고, 다시 접속하면 새 세션이 생긴다(사용자 식별은 P9 범위 밖).
> - 질문 2 (동시 접근): 처음엔 "잘 모르겠다" → 타임라인 표(ⓐ S 제거 → ⓑ 빈 방 확인 → ⓓ T의 JOIN이 방 A 집합을 꺼내 쥠 → ⓒ 방 A 삭제 → ⓔ 쥔 집합에 T 추가 → ⓕ T의 방 목록에 A 추가)로 따라가 내가 찾음: "맵에서 A는 사라지고 T 방 목록엔 A가 남아 ① 깨짐"
>   - 문제 문장 (내 표현, 다듬기 전 "JOIN과 LEAVE가 동시에 일어나면 방 목록 불일치로 메시지 유실" → 반례: 방에 2명이면 삭제가 없어 문제없음): **"마지막 1명 LEAVE로 빈 방 삭제 직전 JOIN이 방을 쥐면 유실"**
>   - 틀로 정리: 같은 방에서 마지막 1명의 `LEAVE`(빈 방 삭제)와 다른 세션의 `JOIN`이, `JOIN`이 방 집합을 꺼낸 뒤·추가하기 전에 삭제가 끼어드는 순서로 일어나면 ①이 깨진다 → 결과: T는 예외 없이 입장 성공으로 알지만, 이후 새로 만들어진 방 A로 오는 메시지를 받지 못한다.
>   - 원인 메모: `ConcurrentHashMap`의 `get`·`remove`·`add` 각각은 안전하지만 "확인 → 삭제", "찾기 → 추가"처럼 여러 단계를 묶은 동작은 안전하지 않다.
> - 질문 3 (넣고 빼기 짝), 내가 채운 표:
>
>   | 사건 | 방 → {세션들} | 세션 → {방들} |
>   |---|---|---|
>   | S가 `JOIN A` | 방 A에 S 추가 (방 A가 없으면? → 설계에서 결정) | S의 목록에 A 추가 |
>   | S가 `LEAVE A` | 방 A에서 S 삭제, 방 A가 비면 방 삭제 | S의 목록에서 A 삭제 |
>   | S의 연결 끊김 | 세션 → {방들}에서 S의 방들을 꺼내, 그 방들에서만 S 삭제, 빈 방은 삭제 | S 항목 삭제 |
>
>   - 끊김 처리에서 처음엔 "빈 방(C → {})과 S → {}를 빈 값으로 남긴다"고 답함 → 내가 적은 불변식 ②·③에 비춰 보고 "없애야 한다"로 고침. 남기면 끊김마다 빈 항목이 쌓여 메모리 누수가 된다.
>   - 설계로 미룬 작은 선택: 연결은 살아 있는데 방 목록이 빈 `S → {}`를 지울지 남길지 (①~③ 어느 것도 깨지 않음)
>   - 끊김 처리에도 질문 2의 경쟁이 생기는가 → 내 답: "생깁니다. 따로 그 부분에 대한 방어 조치를 안했기 때문입니다." 보충: 구조적 원인은 끊김 처리에도 같은 "빈 방 확인 → 삭제" 2단계가 있다는 것. 문제는 `LEAVE`·끊김이 아니라 "빈 방 삭제" 동작 자체에 있으므로, 설계에서 한 곳에 모아 다룬다.
> - 질문 4 (비용 증가): 정의 초반에 확인 — 방 → {세션들}만 있으면 끊김 정리 비용이 전체 방 수에 비례한다 → 세션 → {방들} 추가로 해결
> - 질문 5 (확인 방법):
>   - 내 답: "스레드 여러 개로 동시에 LEAVE·JOIN, 여러 번 반복" / 반복마다 "① 두 매핑이 서로 일치하는지 검사"
>   - P1-1보다 어려운 점: 매 반복마다 "방에 정확히 1명" 상태로 되돌려야 하고, 깨지는 틈(꺼낸 뒤·추가 전)이 좁아 두 스레드를 같은 순간에 출발시켜야 한다. 1,000번 통과해도 안전하다는 결론은 안 나오므로 **방어 없는 코드로 먼저 실패를 재현**한 뒤 고친다.
>   - 검사 방법: 양방향으로 훑는다(방의 각 세션 → 그 세션 목록에 방이 있나 / 세션의 각 방 → 맵에 그 방이 있고 세션이 들어 있나). 이 경쟁은 두 번째 방향에서 걸린다. ②(빈 방 없음)도 함께 검사.
>   - 설계로 넘길 점: 테스트가 두 매핑 상태를 들여다볼 방법(조회용 메서드 등)이 필요하다.
> - 질문 6 (범위):
>   - 서버 2대: 내 답 "서로 세션 당 방, 방이름 당 세션을 알지 못합니다" → 매핑이 서버 메모리마다 따로 있어 같은 방 A가 서버 수만큼 쪼개지고, 다른 서버의 같은 방 사용자에게 메시지가 가지 않는다.
>   - 서버 재시작: 매핑이 사라지지만 WebSocket 연결도 함께 끊기므로, 다시 접속한 클라이언트가 새 세션으로 `JOIN`부터 다시 한다. 불일치는 남지 않는다.
>   - 다루지 않는 근거 (내 답): "P1 범위는 단일 서버이고 다중 서버는 문제 재현 후 도입합니다" → 로드맵 P6(다중 서버, 선행 P4·P5).
> - 1단계 결과: 불변식 ①~③, 문제 문장 1개(빈 방 삭제 경쟁, `LEAVE`·끊김 공통), `JOIN`·`LEAVE`·끊김별 두 매핑 갱신 표.
> - 설계(3단계)로 넘길 것: 빈 방 삭제를 한 곳에 모아 안전하게 만드는 방법, 없는 방 `JOIN` 시 생성/거절, 이미 들어간 방 재`JOIN`, 연결된 세션의 빈 `S → {}` 유지 여부, 테스트가 두 매핑을 조회할 방법, 경쟁 재현 테스트 방식(같은 순간 출발, 매 반복 초기화).

> 고민 진행 (2026-10-24):
> - 처음 생각: "각 `LEAVE`·`JOIN` 처리 때까지 락을 잡는다" → 락 범위 선택: 전체 락 하나 / **방마다 락(내 선택, 락 객체는 방마다 존재)**
> - 반례 (타임라인으로 내가 확인): 스레드 2가 방 A를 꺼내 락 대기 → 스레드 1이 락 안에서 S 제거·맵에서 방 A 삭제 후 락 해제 → 스레드 2가 락을 잡고 삭제된 방에 T 추가 → "맵에서 A는 사라지고 T는 삭제된 방에 들어가 ① 깨짐". 방마다 락만으로는 해결되지 않는다.
>   - 원인: 락은 락 안의 동작끼리만 막는다. "방 찾기"는 락 바깥, "추가"만 락 안에 있었다.
> - 다음 생각: "방 찾기까지 하나의 락으로 건다" → 방을 찾기 전에 잡을 수 있는 락은 방 락이 아니라 맵 쪽 락, 즉 전체 락 하나가 된다.
> - 대안: 방마다 락 + 락을 잡은 뒤 재확인. 확인 대상은 "방 A가 있는가"가 아니라 "맵의 방 A가 내가 쥔 바로 그 객체인가"(그사이 다른 `JOIN`이 같은 이름의 새 방을 만들 수 있음). 다르면 락을 놓고 처음부터 다시. 같은 객체 비교·재시도·락 안 삭제를 모두 지켜야 한다.
>
>   | 방법 | 경쟁을 막는가 | 대가 |
>   |---|---|---|
>   | 방마다 락 (찾기는 락 밖) | 아니오 | — |
>   | **전체 락 하나** | 예 | 서로 다른 방 작업도 줄을 선다 |
>   | 방마다 락 + 재확인 | 예 | 객체 비교·재시도·락 안 삭제 규칙 |
>
> - 결정 (내 선택): **"전체 락 진행 후 문제 상황 발생 시 방마다 락 + 재확인으로"** — 줄 서기가 실제 문제인지 아직 재현되지 않았으므로 단순한 쪽에서 시작한다. 처리량은 P1-7 k6 측정에서 처음 확인한다.

> 정리 (2026-10-24):
> - 배운 것 (내 표현, 원문): "세션, 방 서로간의 정합성을 보장된 매핑을 확인하기 위해 테스트를 진행 후 구현하였다. 정해야할 것은 락을 어느 위치에, 어떤 락을 선정할 것인지에 대해서였는데, 기준이 전체락을 할지, 방마다의 락과 재확인을 하는 방향으로 갈것인지에 대한 선택이었다. 두개 모두 진행하였고 실제로 방이 많고 입장/퇴장이 많은 경우에만 락과 재확인이 더 성능이 좋았다. 하지만 지금은 구현 초반이라 전체락으로 선택하였고 추후에 진행 예정이다." / "락이 필요한 이유는 방찾기에서 락을 잡고서 다른 요청에서 방을 찾을때 변경되기 전에 변경유무를 알지 못해 정합성이 어긋나는 일이 발생될 수 있기 때문이다."
> - 원문에서 고친 점:
>   - 방마다 락이 앞선 조건은 "방이 많고 입퇴장이 많을 때"가 아니라 **서로 다른 방에서 동시에 입퇴장이 몰리고 방이 유지될 때**다. 같은 방이거나 경쟁이 적으면 오히려 느렸다.
>   - 전체 락을 고른 이유는 "초반이라서"가 아니라, 이득이 실제 병목이라는 근거가 없고 대가(규칙 4개, 실행 도중 전체 상태를 볼 수 없음)는 확인됐기 때문이다. 전환은 예정이 아니라 조건부다(P1-7에서 락 대기가 병목으로 확인되면).
>   - 락이 필요한 이유: 락이 이미 있어서가 아니라 **락이 없어서**, 여러 단계("방 찾기 → 추가", "빈 방 확인 → 삭제") 사이에 다른 요청이 끼어든다. `JOIN`은 방을 쥔 뒤 그 방이 삭제된 사실을 모르고 버려진 방에 추가한다.
> - 정리한 문장: 세션 ↔ 방 두 매핑의 정합성을 지키려고, 방어 없는 구현에서 문제를 먼저 테스트로 재현한 뒤 구현했다. 정할 것은 락의 범위와 종류(전체 락 / 방마다 락 + 재확인)였다. 둘 다 구현해 비교했고 정확성은 같았다. 방마다 락은 서로 다른 방에서 동시에 입퇴장이 몰리고 방이 유지될 때만 빨랐다(64 스레드 약 3배). 같은 방이나 경쟁이 적을 때는 느렸다(0.64~0.87배). 실행 도중에는 두 매핑을 일관되게 볼 수 없었다. 그래서 전체 락을 택했고, P1-7에서 락 대기가 병목이면 바꾼다.
> - 이어서 이해한 것 (내 표현): 전체 락은 방 찾기부터 두 매핑 갱신까지 메서드 전체를 감싼다. 방마다 락은 방을 찾아야 락을 얻으므로 방 찾기가 락 밖에 남는다. "처음부터 다시"는 "누군가가 삭제하고 다시 생성하면 그 객체로 들어가기 위한 것. 방을 다시 찾고서 받은 객체로". 보충: `computeIfAbsent`는 그 순간의 객체를 돌려줄 뿐이고, 삭제·재생성 대비는 락을 잡은 뒤의 참조 비교(`rooms.get(roomId) != room`)와 다시 시작이 맡는다.
> - 테스트: `RoomRegistryTest`(단위 7개), `RoomRegistryConcurrencyTest`(경쟁 2개: 방어 없음 11회 모두 실패 → 전체 락 5회 모두 통과), `RoomWebSocketTest`(통합 2개: 핸들러 연결 전 실패 → 후 통과), `RoomLockExperimentTest`(EXP-01). `./gradlew test` 42개 통과.

> - 남은 것: `SEND` 처리와 브로드캐스트(락 안에서 목록 복사, 전송은 락 밖)는 P1-4, 파싱 실패 대응은 P1-5.

>   - 순서가 깨지는 경우 (처음 제시한 타임라인이 틀려 다시 그림): 옛 방 [F, X, H], X가 느린 동안 전원 퇴장 → F·H 재입장 → H의 `SEND`가 다른 열쇠로 바로 진행 → F: 안녕→하이, H: 하이→안녕. 드묾.
>   - 내 첫 판단 "받아들이고 넘어간다, 드물고 재현 전이니까" → 반례: 방 객체를 얻으려면 맵 조회(전체 락)가 먼저라 락 순서(방 → 전체 → 세션)와 충돌하고, ADR-0008 대안 C의 재확인·재시도가 다시 들어온다.
>   - 내 답: **"해시값으로 열쇠 배열의 칸을 고른다"** (락 스트라이핑). 이름만으로 계산, 맵·전체 락 불필요, 방 삭제·재생성에도 같은 열쇠, 생성·정리 없음.
>   - 서로 다른 방이 같은 칸에 걸리면 (내 답): "성능 문제, 순서는 지켜지고 쓸데없이 기다리기만 한다"
> - **측정 요청 (사용자: "테스트에 이것도 꼭 기재해서 테스트해주세요")** → 4단계에서 EXP-02로 실행:
>   - 비교: 열쇠를 얻는 비용 — (가) 해시로 배열 칸 고르기 / (나) 전체 락 안에서 맵으로 방 객체 찾기 + 방 락 후 재확인
>   - 조건: 스레드 1개 / 여러 개, 서로 다른 방 / 같은 방, 방 삭제·재생성이 섞인 경우 (EXP-01과 같은 축)
>   - 실행 전 예상: 계산 자체는 둘 다 매우 짧아 차이가 작고, 차이는 (나)의 전체 락 대기·재시도에서 난다. 실제 숫자는 측정 전이라 기록하지 않음.
> - 클래스 나누기 (부품 역할 표를 보고 내 답): "1은 RoomRegistry, 2·3·4는 새 클래스 … 브로드캐스트 전용" → 반례: 전송 메서드(3)는 P1-5 에러 응답 같은 유니캐스트도 쓴다. 브로드캐스트 클래스에 두면 에러 응답이 브로드캐스트에 의존하거나 세션 락을 건너뛴다 → 내 답 "전송 전용 클래스를 따로 만든다, 둘 다 그걸 쓰게"
> - 서버 → 클라이언트 메시지 (내 답): 필드 "type, roomId, sessionId, text" → 반례: A는 자기 sessionId를 모른다(확인 결과 서버 → 클라이언트 전송이 한 곳도 없음) → 내 답 "연결 직후 서버가 sessionId를 알려준다". 표현 방식 (내 답): "ADR-0007처럼 record + sealed interface, 일관성 때문에" (보충: 문자열 조립은 따옴표 하나로 JSON이 깨짐). 필드 이름은 클라이언트 `SEND`와 맞춰 `content`로 둠.
>
> 설계 확정 (2026-10-24) — [ADR-0009](../../adr/0009-broadcast-per-session-and-per-room-lock.md), [ADR-0010](../../adr/0010-typed-server-message-model.md):
> - 구성:
>
>   | 클래스 | 책임 | 부품 |
>   |---|---|---|
>   | `RoomRegistry` | 매핑 정합성 + 멤버 확인·복사 메서드 추가 (전체 락) | 1 |
>   | `RoomBroadcaster` (새) | 방 락 배열(락 스트라이핑, 64칸) + 복사본 순회 전송. 비멤버면 `false` | 2, 4 |
>   | `SessionSender` (새) | 서버 → 클라이언트 전송의 유일한 입구, `synchronized (session)`. 실패해도 예외를 밖으로 던지지 않고 결과만 돌려줌 | 3 |
>   | `ServerMessage` (새) | sealed interface + `ConnectedMessage(sessionId)`, `ChatMessage(roomId, sessionId, content)` → `CONNECTED`, `MESSAGE` | — |
>   | `ChatWebSocketHandler` | 연결 직후 `CONNECTED` 전송, `SEND` → `RoomBroadcaster` | — |
>
> - 락 순서: 방 락 → 전체 락(멤버 확인·복사 동안만) → 세션 락. 역방향 경로 없음.
> - JSON 변환은 브로드캐스트당 한 번.
> - 테스트 시나리오:
>   1. (실제 연결) `SessionSender` 동시 전송 ②: 서버 쪽 세션에 여러 스레드가 번호 붙은 메시지를 동시에 전송 → 서버 예외 수, 클라이언트 수신 개수, JSON 형식, 중복·누락을 모두 기록. 방어 없는 구현(직접 `sendMessage`)으로 먼저 실행.
>   2. (가짜 세션) `RoomBroadcaster` 기본: 멤버 전원(본인 포함) 수신, 다른 방 격리, 비멤버 `SEND` → `false`·아무도 안 받음, 한 명 전송 실패해도 나머지 수신.
>   3. (가짜 세션 + 전송 지연) 순서 ④: 같은 방에 여러 스레드가 동시에 `SEND` → 모든 멤버의 수신 목록이 같은 순서인가. 방 락 없는 구현으로 먼저 실행.
>   4. (가짜 세션 + 멈춤) B 케이스 ①: 첫 전송에서 멈춘 사이 B가 `JOIN` → 재개 후 B는 받지 않음. 원본 순회 구현으로 먼저 실행.
>   5. (단위) 락 스트라이핑: 같은 이름이면 같은 락, 방 삭제·재생성 후에도 같은 락.
>   6. (통합) 첫 메시지가 `CONNECTED` + sessionId, `JOIN` → `SEND` 전체 흐름, 다른 방은 받지 않음.
>   7. (관찰) 연결을 끊은 뒤 전송 → 실패가 `afterConnectionClosed` 호출로 이어지는가.
>   8. (측정, EXP-02) 열쇠 획득 비용: 해시 칸 vs 방 객체 + 재확인.
> - 확인할 예상 (실행 전): 1은 섞임 또는 예외 중 무엇이 나올지 모름. 3·4는 방어 없는 구현에서 실패. 7은 모름.
>
> 구현·검증 진행 (2026-10-24, 실제 실행):
> - 시나리오 1 (`SessionSendConcurrencyTest`, 스레드 8개 × 200번 = 1,600번, 메시지 약 1KB):
>   - 방어 없음(세션에 직접 `sendMessage`): 5회 모두 실패. 서버 예외 1,475~1,564번, 클라이언트 수신 59~125개(예외 + 수신 = 1,600). 형식 깨짐 0, 중복 0, 서버 세션은 계속 open. 예외는 모두 `IllegalStateException: The remote endpoint was in state [TEXT_PARTIAL_WRITING] which is an invalid state for called method`.
>   - **예상과 다름:** 섞이지 않았다. Tomcat이 "쓰는 중" 상태에서 다른 스레드의 쓰기를 예외로 거절한다 → 실제 증상은 섞임이 아니라 **유실**.
>   - 질문 3 결정의 증거 (내 답): "전송 실패만 보고 세션을 빼지 않는다, 살아있는 세션을 뺄 뻔했다" — 1,500번 넘게 실패하는 동안 연결은 살아 있었다.
>   - `SessionSender`(`synchronized (session)`, 실패 시 `false`) 적용 후: 5회 모두 통과(실패 0, 1,600개 모두 수신). 전체 테스트 44개 통과.
> - 시나리오 3·4 (`RoomBroadcasterTest`, 가짜 세션. 3: 멤버 4명이 각자 100번 동시 `SEND`, 전송마다 0~20µs 무작위 지연 / 4: 첫 전송에서 멈춤 → B `JOIN` → 재개):
>
>   | 구현 | 시나리오 4 (①) | 시나리오 3 (②) |
>   |---|---|---|
>   | 방어 없음 (원본 순회, 방 락 없음) | 5회 모두 실패: `ConcurrentModificationException` | 5회 모두 실패: index 14~219에서 순서 갈림 |
>   | 복사만 (전체 락 안에서 `Set.copyOf`) | 5회 모두 통과 | 5회 모두 실패: index 10~39 |
>   | 복사 + 방 락 (락 스트라이핑 64칸) | 5회 모두 통과 | 5회 모두 통과 |
>
>   - 예상과 다른 점: 시나리오 4는 "B가 받음"이 아니라 **루프 중단**(CME)으로 나타났다. 그 결과 C도 받지 못했다. 문제 문장 ①의 두 번째 예상 증상과 같다.
>   - 예상과 같은 점: 복사는 받는 사람만 정하고 순서는 지키지 못한다. 각 단계가 막는 문제가 하나씩 통과로 바뀌었다.
>   - 전체 테스트 46개 통과.
>   - 내 해석: "복사를 추가하면서 추후에 추가된 B는 안받는걸 확인. 그리고 같은 순서는 방 락 추가로 한 스레드로 처리하게 만들어서 방어되었다" → 보충: "한 스레드로"가 아니라 "한 번에 한 스레드씩". 보내는 Tomcat 스레드는 여럿이고 방 락 앞에서 차례로 줄을 선다(진짜 한 스레드는 고르지 않은 대기열 + 전담 스레드 안).
> - 시나리오 2·5 (`RoomBroadcasterTest` 5개 추가): 구현이 이미 있어 처음 실행에서 모두 통과 → 테스트가 잘못된 구현을 잡는지 구현을 일부러 바꿔 확인(변이 4개, 확인 후 원복). 3개는 잡았고, **변이 3(`floorMod` 대신 `Math.abs(hash) % n`)은 못 잡았다**: `Integer.MIN_VALUE % 64 == 0`이라 64칸에서는 `abs` 방식도 우연히 맞는다. 처음 테스트 주석의 "음수 인덱스가 된다"는 설명이 틀려 정정. `floorMod`는 칸 수를 바꿔도 안전하게 하려는 선택으로 유지. 전체 테스트 51개 통과.
> - 시나리오 6 (`ChatBroadcastWebSocketTest`, 실제 클라이언트 3개): 구현 전 두 테스트 모두 실패("받은 메시지=[]", 서버 → 클라이언트 전송이 없음) → `ServerMessage`(`CONNECTED`·`MESSAGE`)·`ServerMessageWriter` 추가, 핸들러에서 연결 직후 `CONNECTED`, `SEND` → `RoomBroadcaster` 연결 후 5회 모두 통과. 중간에 테스트 쪽 실수(B의 확인용 `MESSAGE`를 A의 메시지로 집음)를 고침.
>   - 다른 방 격리를 실제 연결에서 확정하는 방법: A가 R에 보낸 뒤 Q에 "울타리" 메시지를 보낸다. 같은 연결의 메시지는 서버가 차례로 처리하므로, C가 "울타리"를 받은 시점에 "안녕"이 없으면 받지 않은 것으로 확정. 일부러 모든 방에 보내게 바꾸자 이 검사가 실패함을 확인(원복). 전체 테스트 53개 통과.
