# Phase 01. 최소 실시간 채팅 서버 — 계획

- 상태: 진행 중
- 시작일: 2026-10-24
- 선행 Phase: P0

## 학습 목표

- WebSocket 연결의 수명주기(handshake → message → close)와 정상·비정상 종료의 차이를 이해한다.
- 방 관리와 브로드캐스트를 직접 구현하면서 생기는 문제(동시 수정, 끊긴 세션, 동시 전송)를 테스트로 재현하고 해결한다.
- 이후 Phase의 비교 기준이 될 기준 성능을 측정한다.

## 문제 정의

HTTP 요청/응답만으로는 서버가 클라이언트에게 먼저 메시지를 보낼 수 없다. polling은 주기에 따라 부하와 지연 중 하나를 포기해야 한다.
WebSocket은 연결과 frame 전달만 제공하므로, 채팅방 단위의 전달(방 관리·브로드캐스트·격리)은 애플리케이션이 책임져야 한다.

## 범위 / 비범위

**범위**

- WebSocket 연결과 종료 (정상 close, 비정상 단절)
- JSON 메시지 모델 (입장·퇴장·전송)
- 채팅방 및 세션 관리 (방 → 세션 매핑)
- 같은 방 브로드캐스트, 다른 방 메시지 격리
- 잘못된 입력 처리
- 최소 관측: Micrometer 커스텀 메트릭 (활성 세션 수, 메시지 처리량) — [CHG-002](../../changes/002-early-minimal-observability.md)
- k6 기준 성능 측정 — [CHG-001](../../changes/001-move-baseline-perf-to-phase1.md)
- (선택) 느린 소비자 실험

**비범위**

- 메시지 저장·조회 (P2)
- 인증·인가, WebSocket 보안 (P9)
- 서버 간 메시지 전달 (P6)
- STOMP, SockJS ([ADR-0004](../../adr/0004-raw-websocket-over-stomp.md))
- 클라이언트 UI (테스트 클라이언트와 k6로 검증)

## 시작 결정

메시징 방식은 Raw WebSocket(`WebSocketHandler`)으로 시작한다 — [ADR-0004](../../adr/0004-raw-websocket-over-stomp.md).

## 원인 가설 (구현하며 확인할 것)

- 방 → 세션 매핑을 일반 컬렉션으로 두면, 브로드캐스트 중 입장·퇴장이 일어날 때 동시 수정 문제가 생긴다.
- 비정상 단절 시 close frame이 오지 않으므로, 서버가 단절을 곧바로 알지 못하고 끊긴 세션이 매핑에 남는다.
- 같은 세션에 여러 스레드가 동시에 `send`하면 실패한다.
- 브로드캐스트를 순차 반복으로 하면, 느린 세션 하나가 같은 방 전체의 전달을 지연시킨다.

> 메모: 메시징 방식 선택(Raw vs STOMP)은 Phase 시작 결정으로 ADR-0004에 기록했다. 이 과제의 고민 주제는 "정상 close와 비정상 단절을 서버가 각각 언제, 어떻게 알게 되는가"다.
> 고민 결과: 연결 시 세션 등록, 종료 시 제거. 비정상 단절은 서버 주도 WebSocket ping/pong으로 감지한다 — [ADR-0005](../../adr/0005-websocket-ping-pong-heartbeat.md).
> 설계 메모: 세션 저장소는 `ConcurrentHashMap.newKeySet()` — [개념 노트](../../learning/session-store-concurrency.md).
>
> 설계 확정:
> - 구성: `WebSocketHandler` 구현체(연결 시 등록, 종료 시 제거), 세션 저장소, 엔드포인트 `/ws`
> - 테스트 ① 동시 등록(단위): 출발 신호(`CountDownLatch`)로 N개 스레드가 동시에 add → `size == N`. `HashSet`으로 먼저 실패를 재현한 뒤 교체
> - 테스트 ② 연결 시 등록(통합): 실제 WebSocket 클라이언트 연결 → 저장소에 세션 1개
> - 테스트 ③ 정상 종료 시 제거(통합): 클라이언트 close → 저장소에서 제거
> - heartbeat(ADR-0005)는 비정상 종료와 함께 P1-5에서 다룬다.
>
> 구현·검증 결과 (2026-10-24, 실제 실행):
> - ① `HashSet`: 10회 모두 실패, 확인한 6회는 10000개 중 6611~8546개만 남음(예외 없음) → `ConcurrentHashMap.newKeySet()` 교체 후 10회 모두 통과
> - ②·③ 구현 전: handshake 404로 실패 → `ChatWebSocketHandler`·`WebSocketConfig` 구현 후 통과
> - `./gradlew test` 전체 4개 통과
>
> 정리 (2026-10-24):
> - 배운 것 (내 표현): "예외를 주지 않기 때문에 잃어버린 유실에 관해 알 수가 없습니다."
> - 보충: 동시성 버그는 로그·알림 없이 사용자 증상("가끔 메시지가 안 와요")으로만 드러나고, 부하 상황에서만 확률적으로 생겨 개발 환경에서 재현되지 않는다. 그래서 실패하도록 설계한 테스트로 미리 잡고, 운영에서는 접속자 수 메트릭(P1-6)과 실제 연결 수의 불일치로 간접 감지한다.
> - 남은 것: 비정상 단절 감지(heartbeat)는 P1-5로 이관.

### P1-2 JSON 메시지 모델
- [x] 1. 정의: 요구사항과 문제 정의
- [x] 2. 고민: 원인·해결책 직접 고민, 힌트, 대안 비교 → (필요 시) ADR
- [x] 3. 설계: 최소 설계와 테스트 시나리오 확정
- [x] 4. 구현·검증: 실패하는 테스트 → 구현 → 통과, 예상 vs 실제 비교
- [ ] 5. 정리: 결과 분석, 회고 기록

> 메모: 메시지 종류(`JOIN`·`LEAVE`·`SEND`)와 필드(`roomId`, `content` 등)를 정한다.
>
> 정의 (2026-10-24):
> - 연결(`/ws` 접속)과 방 입장은 다른 일이다. 입장도 메시지의 한 종류다.
> - 한 세션이 여러 방에 동시에 참여할 수 있다(다중 방). 그래서 서버가 세션만 보고 대상 방을 정할 수 없고, `LEAVE`·`SEND`에도 `roomId`가 필요하다. 1세션 1방 모델과의 비교는 설계 단계에서 ADR로 남긴다.
> - 원칙: 서버가 이미 확실히 아는 것(누가 보냈는지 = 세션)은 메시지에서 받지 않고, 받아도 믿지 않는다. 클라이언트만 아는 것(어느 방에, 무엇을)은 메시지에 담는다.
>
> | type | 필드 | 서버가 확인할 것 (P1-3·4) |
> |---|---|---|
> | `JOIN` | `roomId` | 방 존재 여부(또는 생성) |
> | `LEAVE` | `roomId` | 그 방 멤버인지 |
> | `SEND` | `roomId`, `content` | 그 방 멤버인지 |
>
> - 타입마다 필요한 필드가 다르다 → "2. 고민"의 주제: 이를 Java로 어떻게 표현할 것인가.
> - 경계: P1-2는 메시지만 보고 알 수 있는 실패를 **판별**한다(① JSON 파싱 실패 ② 모르는 `type` ③ 필수 필드 누락). 서버 상태가 필요한 검사(비멤버의 `SEND` 등)는 P1-3·4, 판별된 실패에 대한 **대응**(에러 응답 형식, 연결 유지 여부)은 P1-5에서 다룬다.
>
> 고민 결과 (2026-10-24):
> - 처음 생각: 클래스 하나(`type`·`roomId`·`content`)로 받고 controller 단에서 검증.
> - 반례: 단일 클래스는 JOIN에 붙은 `content`도 통과시키고, "SEND일 때만 content 필수" 같은 조건부 검증을 if문으로 써야 하며, 새 타입의 처리 분기를 빠뜨려도 컴파일러가 알려 주지 않는다. Raw WebSocket(ADR-0004)에는 controller·`@Valid`가 없고, MVC에서도 검증은 controller 호출 전 바인딩 단계에서 일어난다.
> - 비교: A 단일 클래스 / **B 타입별 record + sealed interface (Jackson `@JsonTypeInfo`로 `type` 기준 역직렬화)** / C 봉투 `{type, payload}` (와이어 형식 변경, 현재 과함) → **B 채택**. 새 의존성 없음(Jackson 3.1.7 이미 포함).
> - 위치: 핸들러(입출력)와 분리된 파서가 `String` → `ClientMessage` 변환 중에 ①②③을 판별한다.
> - 열린 점: ③ 필수 필드 누락은 Jackson이 자동으로 걸러 주지 않을 것으로 예상(null 필드로 record 생성) → 설계 단계 테스트로 확인.
> - ADR 후보: 다중 방 vs 1세션 1방, 메시지 표현 방식(A/B/C).
>
> 설계 확정 (2026-10-24) — [ADR-0006](../../adr/0006-multi-room-per-session.md), [ADR-0007](../../adr/0007-typed-client-message-model.md):
> - 구성: `ClientMessage` sealed interface + `JoinMessage(roomId)`·`LeaveMessage(roomId)`·`SendMessage(roomId, content)` record, `String` → `ClientMessage` 파서. 실패는 파서가 하나의 예외 타입으로 감싸서 던진다(대응은 P1-5).
> - 검증 위치: 각 record의 compact constructor. `roomId`·`content`는 `null`·`""`·공백만 → 거절. `" 안녕 "`은 그대로 보존.
> - 모르는 필드(`sender`, `JOIN`의 `content` 등): 무시.
> - 범위: 파서와 단위 테스트까지. 핸들러에 연결해 메시지를 처리하는 일은 P1-3에서 한다.
> - 테스트 시나리오 (파서 단위 테스트):
>   1. `JOIN`·`LEAVE`·`SEND` 정상 → 해당 record와 필드 값
>   2. JSON 문법 오류 → 실패
>   3. 모르는 `type`, `type` 누락 → 실패
>   4. `roomId` 누락·`null`·`""`·공백만 (세 타입 각각) → 실패
>   5. `SEND`의 `content` 누락·`null`·`""`·공백만 → 실패
>   6. `content: " 안녕 "` → 공백 포함 그대로 보존
>   7. 모르는 필드 포함(`"sender":"bob"`, `JOIN`의 `content`) → 무시하고 성공
>   8. 파서 없이 `new SendMessage("A", null)` 직접 생성 → 예외
> - 확인할 예상 (실행 전): 생성자 검사가 없으면 Jackson이 `null`로 채워 record를 만든다 / 생성자 예외는 Jackson 예외로 감싸진다 / Jackson 3의 모르는 필드 기본 동작.
>
> 구현·검증 결과 (2026-10-24, 실제 실행):
> - 생성자 검사 없는 record: `ClientMessageParserTest` 27개 중 17개 실패 — 시나리오 4(12개)·5(4개)·8(1개) 전부. 필수 필드가 누락·`null`·`""`·공백만이어도 Jackson은 예외 없이 객체를 반환했고, `new SendMessage("A", null)`도 생성됐다 → 예상대로 Jackson은 필수 여부를 모른다.
> - 같은 실행에서 시나리오 7(모르는 필드)은 `JsonMapper.builder().build()` 기본값만으로 통과 → Jackson 3.1.7 기본값은 무시. 정책을 드러내려고 `FAIL_ON_UNKNOWN_PROPERTIES`를 명시적으로 끄도록 바꿨다.
> - compact constructor 검사 추가 후: 27개 모두 통과, `./gradlew test` 전체 31개 통과.
> - 예외 감싸기 (`SendMessage` content 누락으로 확인): `IllegalArgumentException` → Jackson `ValueInstantiationException` → 파서의 `InvalidMessageException`.

## 테스트 시나리오

세부 시나리오는 각 과제의 "3. 설계"에서 확정한다. Phase 수준에서 반드시 통과해야 할 항목은 다음과 같다.

| # | 검증 항목 | 기대 결과 |
|---|---|---|
| 1 | 연결과 정상 종료 | 연결 시 세션 등록, close 후 세션 제거 |
| 2 | 비정상 단절 | 일정 시간 안에 끊긴 세션이 감지·제거됨 |
| 3 | 같은 방 브로드캐스트 | 같은 방의 모든 클라이언트가 메시지를 받음 |
| 4 | 다른 방 격리 | 다른 방 클라이언트는 메시지를 받지 않음 |
| 5 | 잘못된 입력 | 서버가 죽지 않고 오류 응답 또는 무시, 다른 연결에 영향 없음 |
| 6 | 동시 입장·퇴장 중 브로드캐스트 | 예외 없이 전달됨 |
| 7 | 메트릭 | 활성 세션 수·처리량이 실제 연결·전송과 일치 |

## 완료 기준

- 테스트 시나리오 1~7을 자동화 테스트로 실제 실행해 통과
- k6 기준 성능을 실제로 측정하고 조건과 함께 `experiments/`에 기록
- 과제 P1-1 ~ P1-7의 5단계 체크리스트 완료 (P1-8은 선택)
