# EXP-01. 전체 락 vs 방마다 락 + 재확인

- 날짜: 2026-10-24
- 과제: P1-3 채팅방 및 세션 관리
- 관련: [ADR-0008](../../../adr/0008-room-registry-global-lock.md), [ISSUE-03](../issues/03-join-into-deleted-room.md)
- 코드: `RoomRegistry`(전체 락, 실제 코드), `PerRoomLockRoomRegistry`(방마다 락 + 재확인, 실험용 테스트 코드), `RoomLockExperimentTest`
- 실행: `RELAY_EXPERIMENT=true ./gradlew test --tests 'com.relay.room.RoomLockExperimentTest'` → `build/experiments/room-lock.md`
- 환경: 8코어 노트북, Java 21.0.11, mock 세션, 실제 I/O 없는 반복 루프

## 질문

두 방식은 **정확히 어떤 요소에서** 차이가 나는가?

## 실행 전 예상 (내 표현)

> "전체락인 경우 64개의 스레드라면 대기가 생겨 시간이 많이 걸릴 거 같습니다. (가) 서로 다른 방은 락 + 재확인, (나) 같은 방 하나는 두개 별 차이 없을 거 같습니다."

## 측정 방법

- ① 정확성: `RoomRegistryConcurrencyTest`와 같은 두 경쟁 시나리오(방 1,000개 × 시도 200회).
- ②③④ 처리량: 스레드마다 `JOIN` → `LEAVE`를 반복한다. 300ms 예열 뒤 1초를 재고, 3회 중 중앙값을 쓴다. 스레드 1/4/16/64.
  - (가) 스레드마다 다른 방. 스레드가 방에 혼자라 `LEAVE`할 때마다 방이 삭제되고 다음 `JOIN`에서 다시 만들어진다.
  - (가') 스레드마다 다른 방, 방마다 상주 세션 1명. 방이 삭제되지 않는다. 첫 실행에서 (가)의 차이가 예상보다 작게 나와서 락 효과와 방 생성·삭제 비용을 나눠 보려고 추가했다.
  - (나) 모든 스레드가 같은 방 하나.
- ⑤ 실행 도중의 일관성: 스레드 16개가 (가)를 도는 동안, 관찰 스레드가 1초 동안 두 매핑의 스냅샷을 반복해서 찍고 불변식을 검사한다. 전체 락은 같은 락을 잡고 찍고, 방마다 락은 두 매핑을 차례로 복사한다(전체를 멈출 락이 없다).

## 분석

- **차이를 만드는 요소는 "서로 다른 방의 작업이 실제로 동시에 진행될 수 있는가"다.** 그게 가능한 (가')에서만 스레드가 늘수록 방마다 락이 앞섰다(64개에서 약 3배). 전체 락은 스레드를 4·16·64개로 늘려도 12~13M 근처에 머물렀다. 1개일 때(25~29M)보다도 낮다. 락을 두고 경쟁하는 비용 때문이다.
- **같은 방 하나(나)에서는 방마다 락이 항상 느렸다(0.64~0.87).** 결국 락 하나를 모두가 기다리는 것은 같고, 재확인·`ConcurrentHashMap`·`compute` 같은 추가 비용만 남는다. 예상("별 차이 없음")과 달리 "차이 없음"이 아니라 "추가 비용만큼 느림"이었다.
- **스레드 1개(경쟁 없음)에서도 방마다 락이 느렸다(0.63~0.77).** 동시성의 이득이 없으면 추가 비용만 보인다.
- **방 생성·삭제가 잦으면(가) 이득이 크게 줄었다(64개에서 3배 → 1.4배).** 방마다 락에서는 생성·삭제가 공유 맵(`ConcurrentHashMap`)의 구조 변경과 새 객체 할당을 일으킨다. 이 중 무엇이 얼마를 차지하는지는 나눠 재지 않았다.
- **재시도는 "방이 자주 비는 같은 방"에서만 많았다.** 같은 방에 4명일 때는 방이 자주 비어서 1초에 10만 회 넘게 다시 시도했다. 64명이면 방이 거의 비지 않아 재시도가 없었다.
- **방마다 락에서는 실행 도중 두 매핑을 한 순간에 볼 수 없다.** 찍은 스냅샷이 전부 불변식에 어긋났다. 그 이유는 두 가지다.
  - `join`은 락을 잡기 전에 `computeIfAbsent`로 빈 방을 맵에 먼저 넣는다.
  - 방 쪽과 세션 쪽 갱신 사이에 틈이 있다.
  - 방 락을 하나씩 잡아야 해서 스냅샷 자체도 약 50~180배 적게 찍혔다.
  - 끝난 뒤의 상태는 맞다(①). "실행 도중의 전체 모습"이 필요한 기능(관리자 조회, 전체 방 목록, 메트릭)은 이 방식에서 따로 설계해야 한다.

## 예상과 비교

| 예상 | 실제 |
|---|---|
| 전체 락은 64 스레드에서 대기로 느려진다 | 맞음. 다만 64개가 아니라 4개부터 이미 1개일 때의 절반 정도였고, 그 뒤로는 거의 그대로였다 |
| (가) 서로 다른 방은 락 + 재확인이 빠르다 | 스레드가 많을 때만 맞음. 4개 이하에서는 오히려 느렸고, 방 생성·삭제가 잦으면 이득이 작았다 |
| (나) 같은 방 하나는 별 차이 없다 | 방마다 락이 13~36% 느렸다 |

## 한계

- mock 세션, I/O 없는 반복 루프다. 실제 서버에서는 메시지 파싱·네트워크 I/O가 끼어 락을 잡는 비율이 훨씬 작으므로, 이 차이가 실제 처리량에 얼마나 드러날지는 P1-7 k6 측정 전에는 모른다.
- 스레드 64개는 코어 8개보다 많아 OS 스케줄링 영향이 섞인다.
- 2회(첫 실행 포함 3회) 실행, 조건당 3회 중앙값이다. 경향은 일관됐지만 통계적 검정은 하지 않았다.

## 결론

- ADR-0008의 결정(전체 락 유지)은 바꾸지 않는다. 방마다 락의 이득은 "서로 다른 방 + 스레드 많음 + 방이 오래 유지됨" 조건에서만 나타났다. 실제 서버에서 락 대기가 병목인지는 아직 재현되지 않았다.
- 바꾸게 된다면 처리량 외에 "실행 도중 전체 모습을 볼 수 없다"(⑤)는 대가를 함께 설계해야 한다.
