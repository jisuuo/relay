# EXP-02. 방 락의 열쇠 얻기: 해시 칸 vs 방 객체 + 재확인

- 날짜: 2026-10-24
- 과제: P1-4 같은 방 브로드캐스트와 다른 방 격리 (시나리오 8)
- 관련: [ADR-0009](../../../adr/0009-broadcast-per-session-and-per-room-lock.md), [EXP-01](01-room-lock-comparison.md)
- 계기 (사용자 요청): "테스트에 이것도 꼭 기재해서 테스트해주세요" — 설계 단계에서 "해시로 방번호를 안다면 방 객체로 찾는시간과 해시로 찾는 소요시간차이도 알고싶습니다"
- 코드: `BroadcastLockExperimentTest` (실험용 테스트 코드)
- 실행: `RELAY_EXPERIMENT=true ./gradlew test --tests 'com.relay.room.BroadcastLockExperimentTest'` → `build/experiments/broadcast-lock.md`
- 환경: 8코어 노트북, Java 21.0.11, mock 세션, 실제 I/O 없는 반복 루프

## 질문

브로드캐스트에서 방 락의 열쇠를 얻는 두 방식은 비용이 얼마나 다른가?

- (가) **해시 칸 (채택):** `roomLocks[floorMod(roomId.hashCode(), 64)]` → 그 락 안에서 `membersFor`(전체 락)로 멤버 확인·복사
- (나) **방 객체 + 재확인:** 전체 락 안에서 맵으로 방 객체를 찾음 → 방 객체 락 → 전체 락 안에서 "맵의 방이 아직 그 객체인가" 재확인 + 복사. 다르면 처음부터 다시

## 실행 전 예상

설계 단계 기록 (Claude 예상): "계산 자체는 둘 다 매우 짧아 차이가 작고, 차이는 (나)의 전체 락 대기·재시도에서 난다."

## 측정 방법

- 1건 = 브로드캐스트 한 번의 "열쇠 얻기 → 멤버 확인·복사". 전송은 뺐다.
- 300ms 예열 뒤 1초 측정, 3회 중 중앙값. 스레드 1/4/16/64. 측정 전 두 방식을 모든 조건에서 한 번씩 돌려 JIT 예열.
- 조건
  - ① 서로 다른 방: 스레드마다 자기 방, 방마다 상주 멤버 4명. 방이 유지된다.
  - ② 같은 방 하나: 모든 스레드가 같은 방(상주 멤버 4명).
  - ③ 서로 다른 방 + 생성·삭제: 스레드가 방에 혼자라 매 반복 `JOIN`(방 생성) → 측정 구간 → `LEAVE`(방 삭제).
- 재시도: (나)에서 재확인이 실패해 처음부터 다시 한 횟수.

## 분석

- **두 방식의 차이는 측정 오차 범위 안이다.** 비율이 0.92~1.17 사이에서 실행마다 오르내렸고, 어느 쪽이 일관되게 빠른 조건이 없다. 스레드 1개에서 한 건이 약 150~210ns로 둘이 거의 같다.
- **재시도는 모든 조건에서 0이었다.** 재확인이 실패하려면 "열쇠를 얻은 뒤 ~ 재확인 전"에 방이 삭제돼야 한다. 그런데 브로드캐스트하는 세션은 그 방의 멤버이고, 같은 연결의 `LEAVE`는 서버가 차례로 처리하므로 브로드캐스트 도중에 끼어들 수 없다. 방이 삭제되려면 보낸 사람까지 빠져야 하니, 그 틈에 삭제가 일어날 수 있는 경로는 보낸 사람의 연결 끊김 정리(다른 스레드)뿐이다. ③처럼 매 반복 방을 만들고 지워도 같은 스레드 안에서 차례로 일어나므로 재시도가 없었다.
- **비용을 정하는 것은 열쇠 얻는 방식이 아니라 공유하는 전체 락이다.** 두 방식 모두 멤버 확인·복사에 `RoomRegistry`의 전체 락을 잡는다. 스레드가 4개 이상이면 ①·③에서 둘 다 약 3M/초 근처에 머문다. 서로 다른 방이어도 전체 락에서 한 줄로 서기 때문이다(EXP-01의 전체 락이 12~13M 근처에 머문 것과 같은 현상). (나)는 전체 락을 두 번 잡지만, 그 추가 비용은 경쟁 비용에 묻혔다.
- **같은 방 하나(②)에서는 스레드가 늘수록 둘 다 크게 느려졌다(64개에서 약 0.48M/초).** 모두 같은 방 락 하나를 기다리기 때문이고, 열쇠를 얻는 방식과는 상관없다.

## 예상과 비교

| 예상 | 실제 |
|---|---|
| 계산 자체는 차이가 작다 | 맞음. 1스레드에서 둘 다 약 150~210ns |
| 차이는 (나)의 전체 락 대기에서 난다 | 차이가 나지 않았다. 두 방식 모두 전체 락을 잡아 같은 경쟁을 겪는다 |
| 차이는 (나)의 재시도에서 난다 | 재시도가 0이었다. 보낸 사람이 멤버인 동안 방은 삭제되지 않는다 |

## 한계

- mock 세션, I/O 없는 반복 루프다. 실제 브로드캐스트는 전송(I/O)이 대부분이라, 이 구간의 차이는 실제 처리량에서 더 작아진다.
- 재시도가 생길 수 있는 유일한 경로(브로드캐스트 도중 보낸 사람의 연결 끊김 정리)는 따로 만들어 재지 않았다.
- 스레드 64개는 코어 8개보다 많아 OS 스케줄링 영향이 섞인다. 2회 실행, 조건당 3회 중앙값이며 통계적 검정은 하지 않았다.

## 결론

- **성능으로는 두 방식을 가를 수 없다.** 해시 칸(가)을 고른 근거는 그대로 설계 단계의 두 가지다.
  1. 정확성: 방이 삭제·재생성돼도 같은 이름이면 같은 락이라 순서(불변식 ②)가 깨지지 않는다.
  2. 단순함: 맵·전체 락을 먼저 볼 필요가 없어 락 순서(방 → 전체 → 세션)가 그대로 지켜지고 재확인 루프가 없다.
- ADR-0009 결정은 바꾸지 않는다. 처리량을 높이려면 열쇠 얻는 방식이 아니라 `RoomRegistry` 전체 락의 경쟁을 줄여야 하며, 그것은 P1-7 측정에서 병목으로 확인될 때 다룬다(ADR-0008 재검토 조건).
