# 서버 계층 지도: 메시지 하나가 지나가는 길

- 날짜: 2026-10-25
- 관련: [Phase 1 plan](../phases/phase-01-websocket/plan.md) P1-5 (1. 정의), [ADR-0005](../adr/0005-websocket-ping-pong-heartbeat.md)
- 계기: P1-5 정의 중 FIN·RST, 버퍼, 파일 디스크립터가 설명으로만 쌓여 이해가 끊김. 질문 "현재까지 구현된 기준으로 알아야 할 계층이 어떻게 있나요"
- 상태: 실험 1~3(2026-10-25, 수동 실행)으로 ②·④ 계층 동작 일부 확인. 상한값(`maxConnections` 기본 8192 등)은 일반 설명이며 이 프로젝트에서 측정하지 않음

## 핵심 질문

P1-1~P1-4는 우리 코드 안에서 재현·해결했다. P1-5 끊김은 왜 코드만 보고는 이해가 안 될까?
→ 문제가 생기는 곳(아래 계층)과 보이는 곳(우리 코드)이 다르기 때문이다. 계층을 먼저 그려 둔다.

## 1. 서버 하나 안을 열어 보면

```
 ┌──────────────────────────────────────────────────────────────┐
 │ ⑤ 우리 코드  (com.relay)                                        │
 │                                                              │
 │   ChatWebSocketHandler      입출력만. 연결·메시지·끊김 이벤트 받음      │
 │     ├─ ClientMessageParser  문자열 → JOIN/LEAVE/SEND   (P1-2)   │
 │     ├─ RoomRegistry         방 ↔ 세션 두 매핑, 전체 락     (P1-3)   │
 │     ├─ RoomBroadcaster      방 멤버에게 뿌리기, 방 락       (P1-4)   │
 │     └─ SessionSender        세션 하나에 보내기, 세션 락      (P1-4)   │
 ├──────────────────────────────────────────────────────────────┤
 │ ④ Spring WebSocket                                            │
 │   /ws 경로 연결 → 핸들러 호출, WebSocketSession 객체 제공           │
 │   afterConnectionEstablished / handleTextMessage /            │
 │   afterConnectionClosed 를 "언제" 부를지 결정                     │
 ├──────────────────────────────────────────────────────────────┤
 │ ③ Tomcat  (JVM 안의 웹 서버)                                     │
 │   연결 받기 → 스레드 풀(nio-8080-exec-N)에서 스레드 하나 배정          │
 │   WebSocket 프레임 읽기·쓰기, 연결 수 상한(maxConnections)           │
 ├──────────────────────────────────────────────────────────────┤
 │ ② OS  (macOS 커널)                                              │
 │   소켓 = 파일 디스크립터, 송신 버퍼·수신 버퍼, TCP (ACK·재전송·FIN·RST)  │
 ├──────────────────────────────────────────────────────────────┤
 │ ① 네트워크                                                      │
 │   지금은 localhost라 실제 선은 없음 (그래서 진짜 유령을 못 만듦)         │
 └──────────────────────────────────────────────────────────────┘
```

## 2. 계층마다 지금까지 만난 문제

| 계층 | 하는 일 | 만난 문제 |
|---|---|---|
| ⑤ 우리 코드 | 방·세션 상태와 전송 순서 | 동시 등록 유실(P1-1), 빈 방 삭제 경쟁(P1-3), 순서 뒤섞임(P1-4) |
| ④ Spring | 이벤트를 우리 코드에 전달 | 끊김 신호가 없으면 `afterConnectionClosed`를 부르지 않음 (실험 1) |
| ③ Tomcat | 스레드 배정, 프레임 쓰기 | 같은 세션 동시 쓰기를 예외로 거절(P1-4), 연결 슬롯 상한 |
| ② OS | 버퍼, TCP 신호 | `sendMessage`는 버퍼에 넘기면 성공 (실험 2), 버퍼가 차면 막힘 |
| ① 네트워크 | 실제 전달 | FIN·RST가 사라지는 곳 (localhost로는 재현 불가) |

정리: P1-1~P1-4는 ⑤ 안의 문제였다. P1-5 끊김은 ①·②에서 생긴 일이 ⑤까지 **올라오지 않는** 문제다.

## 3. 용어

- **FIN**: "더 보낼 것 없음" 정상 종료 신호. 받으면 서버 읽기가 EOF로 끝난다.
- **RST**: 즉시 강제 종료 신호. 받으면 서버 읽기가 "Connection reset" 에러로 끝난다.
- 둘 중 하나(또는 WebSocket Close 프레임)가 도착해야 ④가 `afterConnectionClosed`를 부른다. P1-4 관찰: FIN 0ms, RST 2~3ms, 코드 1006.
- **버퍼**: 속도가 다른 두 쪽 사이의 임시 보관함(우체통). 송신 버퍼는 상대 ACK를 받을 때까지 데이터를 지우지 않는다(재전송용).
- **파일 디스크립터(fd)**: OS가 열린 소켓·파일마다 붙이는 번호. 프로세스당 개수 상한(`ulimit -n`)이 있다.

## 4. 실험으로 본 것 (2026-10-25)

### 실험 1: 클라이언트 C를 일시 정지(`kill -STOP`)하고 71초

```
              클라이언트 C                         서버
         ┌──────────────────┐            ┌──────────────────────────┐
 앱       │ node (정지됨 ⏸)   │            │ afterConnectionClosed ✗  │ ← 호출 안 됨
         │ 코드 실행 안 됨     │            │ 매핑: 방 A = {C}  (③ 깨짐) │
         └────────┬─────────┘            └────────────▲─────────────┘
 Tomcat           │                      │ 읽기 대기 중... ("아직 말 없음"과 │
                  │                      │  "사라짐"을 구별 못 함)           │
         ┌────────┴─────────┐            ┌────────────┴─────────────┐
 OS       │ 소켓 ESTABLISHED  │            │ 소켓 ESTABLISHED           │
         └────────┬─────────┘            └────────────▲─────────────┘
 네트워크           └──────── FIN ✗  RST ✗  Close ✗ ──────┘
```

- 원인 → 결과 순서: 신호가 안 옴 → `afterConnectionClosed` 호출 안 됨 → 그래서 세션이 남음.
- 한계: 일시 정지는 진짜 유령의 절반만 흉내 낸다. 앱은 멈췄지만 C 쪽 OS는 살아 있어 TCP 응답(ACK)을 한다.

### 실험 2: 같은 방에서 B가 `SEND` 1개

```
              서버                                    클라이언트 C
  ┌──────────────────────────┐              ┌───────────────────────┐
앱 │ SessionSender.send(C)    │              │ node (정지됨 ⏸)         │
  │   sendMessage → true ✓   │              │ 안 읽음 → 메시지 못 봄     │
  └────────────┬─────────────┘              └───────────▲───────────┘
  ┌────────────▼─────────────┐              ┌───────────┴───────────┐
OS │ 송신 버퍼  Send-Q = 0      │ ── 데이터 ─▶ │ 수신 버퍼 Recv-Q = 84   │ ← 여기 쌓임
  │ (ACK 받아서 비움)          │ ◀── ACK ──── │ (OS는 살아 있어 ACK)     │
  └──────────────────────────┘              └───────────────────────┘
```

- `sendMessage`는 OS에 넘기면 돌아온다. 상대 앱이 읽었는지는 모른다.
- 진짜 유령이면 ACK가 없어 데이터가 서버 송신 버퍼에 남는다.

### 실험 3: B가 1KB `SEND` 20,000개를 몰아 보냄

1차 실행은 내용이 `'x'` 반복이라 `permessage-deflate` 압축으로 메시지당 약 18바이트로 줄어 버퍼가 차지 않았다(2초 안에 전부 도착). 실험 조건 실수 → 무작위 내용으로 다시 실행.

```
            exec-5 (B의 SEND 처리)                     exec-9 (D의 SEND)
  ┌──────────────────────────────────┐        ┌──────────────────────────┐
앱 │ broadcast: 방 A 락 쥠 🔒           │        │ broadcast: 방 A 락 대기 ⏳   │ ← BLOCKED
  │   └ SessionSender: C 세션 락 쥠 🔒  │        └──────────────────────────┘
  ├──────────────────────────────────┤
Tomcat│ sendMessageBlock: 자리 날 때까지   │ ← TIMED_WAITING, 최대 약 20초
  │ 기다림 ⏳                           │
  ├──────────────────────────────────┤        ┌──────────────────────────┐
OS │ 송신 버퍼 Send-Q 145,845 (가득)      │ ─✗─▶   │ C 수신 버퍼 Recv-Q 571,538 │ (C 정지, 안 읽음)
  └──────────────────────────────────┘        └──────────────────────────┘
```

| 시점 | 일 |
|---|---|
| 1~2초 | B가 812개 받고 멈춤 (양쪽 버퍼 가득) |
| 6초 | D(방 A) 5초 동안 못 받음, E(방 Z) 1ms에 받음 |
| 약 20초 | C 전송 `Write timeout` → Tomcat이 C 연결 닫음(1006) → `afterConnectionClosed` |
| 22~23초 | 방 락이 풀려 B가 나머지 전부 받음 |

- 방 락은 버퍼 때문에 새로 걸리는 게 아니다. 순서 보장(P1-4) 때문에 **원래 전송 내내** 쥐고 있고, 버퍼가 차면 쥐는 시간이 길어질 뿐이다.
- 다른 방은 다른 락이라 영향이 없다.
- 쓰는 데이터가 있으면 Tomcat 쓰기 시간 초과가 결국 연결을 닫는다. 쓰는 데이터가 없으면(실험 1) 이 경로도 없다.

## 5. ④ Spring: 핸들러에서 예외가 나면

확인 방법: `spring-websocket-7.0.10.jar`의 `WebSocketHttpRequestHandler`·`ExceptionWebSocketHandlerDecorator`를 `javap -c`로 열어 봄 (2026-10-25). 실험 4에서 실행으로 확인: 깨진 JSON 한 번에 B가 `1011`, reason 빈 값으로 끊김, 이후 정상 `SEND`는 버려짐.

### 우리 핸들러는 포장지 두 겹에 싸여 있다

```
 ④ Spring
 ┌─────────────────────────────────────────────────────┐
 │ ExceptionWebSocketHandlerDecorator   ← 예외를 잡는 겹       │
 │ ┌─────────────────────────────────────────────────┐ │
 │ │ LoggingWebSocketHandlerDecorator  ← 로그 남기는 겹     │ │
 │ │ ┌─────────────────────────────────────────────┐ │ │
 │ │ │ ⑤ ChatWebSocketHandler (우리 코드)             │ │ │
 │ │ └─────────────────────────────────────────────┘ │ │
 │ └─────────────────────────────────────────────────┘ │
 └─────────────────────────────────────────────────────┘
```

실험 로그의 `LoggingWebSocketHandlerDecorator : New ...Session`은 가운데 겹이 남긴 것이다.

### 예외가 나면 일어나는 일

```
⑤ handleTextMessage
     └ parser.parse() → InvalidMessageException 💥  (우리 코드에서 안 잡음)
            │ 위로 올라감
④ ExceptionWebSocketHandlerDecorator.handleMessage
     └ catch → tryCloseWithError()
           ├ 1) ERROR 로그
           └ 2) 세션이 열려 있으면 session.close(SERVER_ERROR)  ← 코드 1011
            │
③ Tomcat   Close 프레임(1011)을 클라이언트에 보내고 연결 종료
            │
④ → ⑤      afterConnectionClosed 호출 → 매핑 정리 (③ 지켜짐)
```

- 예외 하나 = 연결 끊김. 클라이언트는 이유 메시지 없이 닫힘 코드 1011(서버 내부 오류)만 받는다.
- `afterConnectionEstablished`·`handleTransportError`의 예외도 같은 길로 처리된다.
