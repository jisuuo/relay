# 세션 저장소와 동시성: 왜 HashSet이 아니라 ConcurrentHashMap인가

- 날짜: 2026-10-24
- 관련: [Phase 1 plan](../phases/phase-01-websocket/plan.md) P1-1 (3. 설계), [ADR-0004](../adr/0004-raw-websocket-over-stomp.md)
- 상태: `SessionRegistryTest`로 재현·해결 확인 (2026-10-24)

## 핵심 질문

연결 시 세션을 등록하고 종료 시 제거하는 저장소를, 여러 스레드가 동시에 써도 안전하게 만들려면 어떤 자료구조를 골라야 하는가?

## 프로젝트에서의 문제

Tomcat은 연결 이벤트를 스레드 풀의 여러 스레드로 동시에 처리한다. 사용자 A와 B가 동시에 접속하면 서로 다른 스레드가 `afterConnectionEstablished`를 실행하고, 둘 다 **같은 저장소 객체 하나**에 쓴다.

## 1. HashSet

- 중복 없는 집합(Set)을 해시 테이블로 구현한 것. 내부에 `HashMap`을 두고 원소를 key로 저장한다.
- `hashCode()`로 버킷 위치를 바로 계산하므로 `add`·`remove`·`contains`가 평균 O(1)이다. 같은 버킷에 걸리면 `equals()`로 중복을 확인한다.
- **resize**: 원소 수가 `capacity × load factor`(기본 16 × 0.75 = 12)를 넘으면 2배 크기의 새 배열을 만든다. 그리고 **참조(`table`)를 먼저 새 배열로 바꾼 뒤**, 기존 배열의 칸을 하나씩 비우면서(`oldTab[j] = null`) 원소를 새 배열로 옮긴다(JDK 21 `HashMap.resize()` 소스 확인). 옮기는 동안 일부만 옮겨진 **중간 상태**가 존재한다.
  - 정정(2026-10-24): 처음에는 "모든 원소를 다시 배치한 뒤 참조를 교체한다"고 적었다. 블로그 글 평가에서 순서가 틀렸다는 지적을 받았고, JDK 21 소스로 확인해 보니 실제로는 참조를 먼저 바꾼다.
- 스레드 안전하지 않다. 공식 문서도 동시 수정 시 외부 동기화를 요구한다.

## 2. 경쟁 조건 (race condition)

한 줄짜리 코드도 CPU에서는 여러 단계로 실행된다. `count = count + 1`은 **읽기 → 계산 → 쓰기**다. 두 스레드가 이 단계 사이에 끼어들면 결과가 실행 타이밍에 따라 달라진다.

| 시점 | 스레드 1 | 스레드 2 | count |
|---|---|---|---|
| t1 | 읽기 → 0 | | 0 |
| t2 | | 읽기 → 0 | 0 |
| t3 | 쓰기 → 1 | | 1 |
| t4 | | 쓰기 → 1 | **1** (기대값 2) |

- 내 답 — 정상적으로 2가 되려면: "스레드1이 쓰기까지 끝낸 뒤 스레드 2가 읽으면 2"
- `HashSet.add()` 내부의 `size++`, 버킷 연결, resize도 같은 구조라 원소 유실·size 불일치가 생길 수 있다.

### 세션 저장소에서의 결과

resize가 참조를 새 배열로 바꾸기 전에 **기존 배열** 참조를 읽어 둔 스레드가 있다고 하자. 이 스레드가 resize 스레드가 이미 옮기고 비운 칸에 세션을 넣으면, 그 세션은 새 배열로 옮겨지지 않는다. 결국 아무도 보지 않는 기존 배열과 함께 GC 대상이 된다. 예외는 나지 않는다. 이것은 소스 순서에서 추론한 경로 중 하나이며, 이번 유실이 실제로 이 경로로 생겼는지는 확인하지 않았다.

- 내 답 — 사라진 사용자 B에게 생기는 일: "연결은 되어서 전송은 할 수 있지만 메시지가 전달되지 않습니다."
- 보충: 접속자 수가 1 적게 집계되고, heartbeat ping도 B에게 가지 않는다. 서버 로그에 오류가 남지 않아 찾기 어렵다.

## 3. 원자성과 해결 원리

**읽기 → 계산 → 쓰기를 다른 스레드가 끼어들 수 없는 한 덩어리로 만든다** (원자성). 방법은 두 가지다.

- **락**: 열쇠를 가진 스레드만 실행하고 나머지는 기다린다.
- **CAS (Compare-And-Swap)**: "지금 값이 내가 읽은 값과 같으면 바꾸고, 다르면 실패"를 CPU 명령 하나로 실행한다. 실패하면 다시 읽고 재시도한다. 기다리지 않는다.
  - 내 답 — t4에서 스레드 2의 CAS가 실패한 이유: "스레드1이 먼저 바꿔서 값이 달라 실패", 재시도 없이 포기하면: "1"

## 4. 선택지 비교

| 선택지 | 방식 | 세션 저장소에 대한 판단 |
|---|---|---|
| `Collections.synchronizedSet(new HashSet<>())` | Set 전체에 락 하나 | 수천 연결이 한 줄로 대기. 반복 시 직접 락 필요 |
| **`ConcurrentHashMap.newKeySet()`** | 버킷 단위 락 + 빈 버킷은 CAS | 다른 버킷을 건드리는 스레드는 동시에 진행. 반복 중 수정돼도 예외 없음 |
| `CopyOnWriteArraySet` | 쓰기마다 배열 전체 복사 | 연결·종료마다 수천 칸 복사 → 부적합. "거의 안 바뀌고 자주 읽는" 데이터용 |

- 내 선택: ② `ConcurrentHashMap.newKeySet()`
- 처음 내 이유: "접속자가 수천이기에 동시에 버킷을 건드리지만 원자연산을 통해 무조건 락이 해제되어야 가능하도록 해야한다."
- 바로잡은 이해: 핵심은 락 해제가 아니라 **락을 Set 전체가 아니라 버킷 단위로 잘게 나눈다**는 점. 열쇠가 하나(①)가 아니라 칸마다 있다(②).

## 5. 자료구조 선택 기준

1. 어떤 연산이 필요한가? → 추가, 삭제, 전체 반복, 개수
2. 데이터 규칙은? (중복·순서·key 조회) → 중복 없음, 순서 불필요 → Set
3. 연산 빈도는? (읽기 vs 쓰기) → 둘 다 잦음
4. 여러 스레드가 동시에 접근하는가? → 그렇다
5. 규모는? → 수천 → 쓰기마다 전체 복사는 부적합
6. 얼마나 정확해야 하는가? → 아래 열린 질문
7. 위를 만족하는 가장 단순한 것은? → ②

1~2는 구조의 종류(List·Set·Map·Queue)를, 3~6은 같은 종류 안의 구현체를 정한다.

## 열린 질문 / 확인할 것

- `ConcurrentHashMap`의 반복은 weakly consistent다. 반복 도중 추가·삭제된 세션이 이번 반복에 보일 수도 안 보일 수도 있다. 브로드캐스트에서 괜찮은가? → P1-4에서 검토
- ~~테스트로 재현하지 않았다~~ → 확인함: `SessionRegistryTest`(100 스레드 × 100 세션, `CountDownLatch` 출발 신호)에서 `HashSet`은 10회 모두 실패(확인한 6회 6611~8546/10000, 예외 없음), `ConcurrentHashMap.newKeySet()`은 10회 모두 통과.
- 유실이 resize 때문인지, 버킷 연결·`size` 증가 경합 때문인지 각각의 비중은 확인하지 않았다.
