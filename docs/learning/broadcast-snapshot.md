# 브로드캐스트와 스냅샷: 왜 멤버 목록을 복사해서 보내는가

- 날짜: 2026-10-24
- 관련: [Phase 1 plan](../phases/phase-01-websocket/plan.md) P1-4 (1. 정의), [ADR-0008](../adr/0008-room-registry-global-lock.md)
- 계기: P1-4 정의 중 질문. "방 R의 멤버 목록을 복사한 순간 이게 정확히 어떤 원리죠", "복사가 뭔지 모르겠어요", "왜 복사한 순간 그대로를 남겨야하낭"
- 상태: `RoomBroadcasterTest`·`SessionSendConcurrencyTest`·`AbnormalCloseObservationTest`로 확인 (2026-10-24). 아래 5절

## 핵심 질문

방 R에 `SEND`가 오면 "그 순간의 멤버"에게 보내야 한다. 그런데 멤버는 `JOIN`·`LEAVE`·끊김으로 계속 바뀐다. "그 순간"을 어떻게 하나로 정하고, 보내는 동안 바뀌는 목록을 어떻게 다룰까?

## 1. 참조와 복사

Java 변수에는 객체 자체가 아니라 **객체의 위치(참조)**가 들어 있다.

```java
Set<WebSocketSession> targets = members;            // 참조만 하나 더: 같은 집합
Set<WebSocketSession> targets = Set.copyOf(members); // 새 집합을 만들어 원소를 옮겨 담음
```

```
참조 전달                     복사
members ─┐                   members ──▶ [ A, B ]   ← 이후 JOIN/LEAVE 반영
         ├──▶ [ A, C ]       targets ──▶ [ A, C ]   ← 복사한 순간 그대로
targets ─┘
```

비유: 원본 집합은 벽에 걸린 출석부(계속 고쳐짐), 참조 전달은 "벽의 그 출석부 봐", 복사는 **그 순간 출석부를 찍은 사진**이다.

## 2. 왜 그 순간을 남겨야 하나: 전송 방법 세 가지

| | 다른 방을 막나 | 순회가 안전한가 | 받는 사람이 정해지나 |
|---|---|---|---|
| 1. 락 안에서 원본 보며 전송 | 막음 (전송 내내) | 안전 | 정해짐 |
| 2. 락 없이 원본 보며 전송 | 안 막음 | 위험 | 매번 다름 |
| 3. 락 안에서 복사, 락 밖에서 복사본으로 전송 | 거의 안 막음 | 안전 | 정해짐 |

- **1번**: 복사가 필요 없지만 전송은 네트워크 I/O라 느리다. 지금은 전체 락이라 그동안 **모든 방**의 요청이 멈춘다. 한 사람의 네트워크가 느리면 서버 전체가 느려진다.
- **2번**: 순회 중 다른 스레드가 같은 `HashSet`을 바꾼다. `ConcurrentModificationException`으로 루프가 중간에 끊기거나, 예외 없이 누군가를 건너뛸 수 있다(P1-1에서 본 "예외 없는 유실"과 같은 종류). 받는 사람이 타이밍마다 달라서 불변식을 쓸 수도, 테스트할 수도 없다.
- **3번**: 락은 복사하는 짧은 시간만 잡고, 전송은 바뀌지 않는 복사본으로 한다.

→ 복사는 목적이 아니라 **락을 짧게 잡으면서 안전하게 순회하기 위한 수단**이다. 그래서 ADR-0008은 "락 안에서 목록 복사, 전송은 락 밖"을 택했다.

## 3. "복사한 순간"이 기준 시점이 되는 원리

`RoomRegistry`의 모든 변경은 같은 락(`this`)을 잡는다. 복사도 같은 락 안에서 하면 모든 요청이 **한 줄로** 선다.

```
락 획득 순서:  [C JOIN] → [A SEND: 복사] → [B JOIN] → [C LEAVE]
                         ↑ SEND 처리 시점
```

- 복사하는 동안 아무도 목록을 못 바꾸므로 복사본은 그 순간을 정확히 담는다.
- 앞선 변경은 전부 반영되고 뒤의 변경은 하나도 반영되지 않는다. 일부만 반영된 중간 상태가 없다.
- 이렇게 연산이 "이 한 점에서 일어났다"고 말할 수 있는 지점을 **선형화 지점(linearization point)**이라 한다.

결과: 위 순서에서 B(복사 뒤 입장)는 받지 않고, C(복사 뒤 퇴장)는 받는다.

## 4. 락이 막지 못하는 것: 연결 끊김

3번 방식에는 "복사한 뒤 전송하기 전" 틈이 있다. 그럼 1번 방식(락 안에서 전송)이면 문제가 없을까?

- `LEAVE`에 대해서는 그렇다. `leave()`가 락을 기다리므로 전송이 끝날 때까지 C는 목록에서 빠지지 않는다. (사용자 답: "락 잡고 있어서 C가 못 나가니까 안 생긴다")
- 하지만 락이 막는 것은 `removeSession()`이 **목록을 고치는 일**뿐이다. C의 와이파이가 끊기거나 브라우저를 닫아 생기는 **실제 네트워크 연결 종료**는 락과 무관하게 언제든 일어난다.

```
방법 1, 락 잡은 채 전송 중
  A에게 전송 ✓
  (C의 연결이 끊김. removeSession은 락을 기다리는 중)
  C에게 전송 → 이미 닫힌 연결 → 실패
```

→ "목록에는 있는데 실제로는 보낼 수 없는 세션"은 어느 방식에서도 생긴다. 락으로 해결할 문제가 아니라, **전송 실패를 어떻게 다룰지** 따로 정해야 하는 문제다.

## 5. 테스트로 확인한 것 (2026-10-24)

| 구현 | 복사 후 `JOIN`한 B (①) | 멤버 사이 순서 (②) |
|---|---|---|
| 락 없이 원본 순회 (2번 방법) | 5회 모두 `ConcurrentModificationException` → 루프가 끊겨 뒤 순서 C도 못 받음 | 5회 모두 어긋남 |
| 락 안에서 복사 (3번 방법) | 5회 모두 통과 | 5회 모두 어긋남 |
| 복사 + 방 락 (복사부터 전송 루프까지) | 5회 모두 통과 | 5회 모두 통과 |

- 복사는 **받는 사람**만 그 순간으로 고정한다. 두 `SEND`의 루프가 락 밖에서 서로 앞지르는 것은 막지 못한다. 순서까지 지키려면 같은 방의 `SEND`가 한 번에 한 스레드씩 끝까지 보내야 한다(방 락).
- 2번 방법의 실제 증상은 "B가 받음"보다 먼저 **루프 중단**이었다. `HashSet`의 순회는 순회 중 집합이 바뀐 것을 알아채면 예외로 멈춘다(fail-fast).
- 같은 세션에 두 스레드가 동시에 보내면 섞이지 않고 Tomcat이 예외(`TEXT_PARTIAL_WRITING`)로 거절해 메시지가 사라진다. 그동안 연결은 살아 있었다 → 전송 실패만 보고 세션을 정리하면 안 된다.
- close frame 없이 끊겨도(FIN·RST) 서버는 **읽기 쪽**에서 바로 알아채 `afterConnectionClosed`(1006)를 부른다. 끊긴 세션에 보내면 실패(`false`)할 뿐 루프는 계속된다.
- 보낸 사람 A는 보내는 도중에 방에서 나갈 수 없다. 복사 때문이 아니라 **같은 연결의 메시지는 하나씩 차례로 처리**되기 때문이다(A의 `LEAVE`는 `SEND` 처리가 끝날 때까지 대기). 다른 연결인 C는 그사이 나갈 수 있다.

## 남은 질문

- FIN·RST가 서버에 도착하지 않는 끊김(네트워크 단절)은 서버가 알아챌 신호가 없다 → P1-5 heartbeat
- 느린 멤버가 있으면 방 락 앞에서 Tomcat 스레드가 줄을 선다 → P1-8 느린 소비자
