# ADR-0009. 브로드캐스트의 동시성: 세션마다 락 + 방마다 락

- 상태: Proposed
- 날짜: 2026-10-24
- 관련 Phase: P1 (P1-4, P1-8)

## 배경

P1-4 정의 단계에서 브로드캐스트의 불변식을 정했다 ([plan](../phases/phase-01-websocket/plan.md) P1-4, [개념 노트](../learning/broadcast-snapshot.md)).

1. 복사한 순간 방 R의 멤버였던 세션 중 연결이 살아 있는 세션은 반드시 받고, 복사한 순간의 멤버가 아니었던 세션은 받지 않는다.
2. 같은 방의 멤버들은 메시지를 같은 순서로 받는다. (고민 단계에서 추가)

①은 [ADR-0008](0008-room-registry-global-lock.md)의 전체 락 안에서 멤버 목록을 복사하고, 전송은 락 밖에서 복사본으로 하는 방식으로 지킨다. 그런데 전송을 락 밖에서 하면 두 문제가 남는다 (둘 다 아직 재현 전, 예상).

- **문제 ② 같은 세션 동시 전송:** 전송은 받는 사람이 아니라 보낸 사람의 스레드가 한다. 같은 방의 다른 멤버, F가 들어간 다른 방, F 자신의 요청에 대한 응답이 모두 F의 `WebSocketSession` 객체 하나로 모이므로, 여러 스레드가 동시에 `F.sendMessage`를 호출할 수 있다 → 메시지가 섞이거나 덮어씌워질 것으로 예상.
- **문제 ④ 멤버마다 순서가 다름:** 같은 방의 두 `SEND` 스레드가 각자 복사본을 순회한다. 한쪽이 어느 세션에서 기다리는 동안 다른 쪽이 뒤 순서 멤버에 먼저 도착하면, 멤버마다 받는 순서가 달라진다.

## 검토한 대안

### 문제 ②: 같은 세션에 한 번에 한 스레드만 쓰게 하기

| 대안 | 기다리는 범위 | 대가 |
|---|---|---|
| A. 전체 락(ADR-0008)을 전송에도 사용 | 서버 전체 | 느린 전송 하나가 모든 방의 전송·`JOIN`·`LEAVE`를 멈춘다 |
| **B. 세션마다 락: `synchronized (session)` + 전송 메서드 하나** | 같은 세션에 보내는 스레드끼리만 | 모든 전송이 그 메서드를 거쳐야 한다 (직접 `sendMessage` 호출은 컴파일러가 막지 않음) |
| C. Spring `ConcurrentWebSocketSessionDecorator` | 기다리지 않음 (세션별 버퍼에 넣고 반환, 락을 잡은 스레드가 버퍼를 비움) | 시간·버퍼 한도 값을 정해야 하고, 느린 소비자 처리(문제 ③)까지 함께 들어온다 |

### 문제 ④: 복사할 때 정해진 순서를 전송에서도 지키기

| 대안 | 느린 F가 있을 때 | 대가 |
|---|---|---|
| **D. 방마다 락으로 "복사 + 전송 루프 전체"를 감쌈** | 방 R에 `SEND`한 Tomcat 스레드들이 줄 서서 기다림 → 많아지면 스레드 풀이 바닥나 다른 방도 멈출 수 있음 | 방마다 락 객체 |
| E. 방마다 대기열 + 전담 스레드 | 전담 스레드만 묶이고 대기열이 커짐. Tomcat 스레드는 넣고 반환 | 방마다 스레드(방 10,000개면 10,000개), 대기열, 생성·종료 관리 |

## 결정

- 문제 ②: **B.** 서버 → 클라이언트 전송은 메서드 하나로만 하고, 그 안에서 `synchronized (session)`으로 감싼다. 세션 객체가 이미 세션마다 하나씩 있으므로 락을 따로 만들거나 보관·정리할 필요가 없다.
- 문제 ④: **D.** 방마다 락을 잡은 채로 (전체 락 안에서) 멤버 확인·복사를 하고, 복사본 전체에 전송한 뒤 방 락을 놓는다.

함께 정한 규칙:

- 보낸 사람 본인에게도 보낸다. 모두가 서버가 처리한 순서 하나를 같은 순서로 보게 하려고 (클라이언트 시계 기준 정렬은 시계가 사람마다 달라 쓸 수 없다).
- 방 멤버가 아닌 세션의 `SEND`는 아무에게도 보내지 않고 `false`를 돌려준다. 에러 응답은 P1-5에서 정한다 (ADR-0008의 비멤버 `LEAVE`와 같은 방식). 멤버 확인과 복사는 같은 전체 락 안에서 한다.
- 한 멤버에게 전송이 실패해도 다음 멤버에게 계속 보낸다.
- 전송 실패만 보고 세션을 정리하지 않는다. 전송 실패는 연결 종료일 수도, 동시 전송 같은 다른 이유일 수도 있는 애매한 신호다. 살아 있는 세션을 빼면 이후 메시지를 예외 없이 받지 못해 불변식 ①이 깨진다. 정리는 `afterConnectionClosed` 한 경로에서만 하고, close frame이 오지 않는 비정상 단절은 heartbeat가 연결을 닫아 같은 경로로 오게 한다 (P1-5, [ADR-0005](0005-websocket-ping-pong-heartbeat.md)).

## 근거

- B와 D는 각 문제를 막는 가장 단순한 방법이다. C와 E가 더 나은 점은 모두 **느린 소비자(문제 ③)**에 관한 것인데, 문제 ③은 아직 재현되지 않았다. 재현된 문제가 있을 때만 복잡한 방법을 도입한다는 원칙([roadmap](../roadmap.md))에 따라 P1-8로 넘긴다. 사용자 결정: "P1-8로 넘긴다, 아직 재현된 문제가 없다", "방마다 락, 느린 소비자는 아직 재현 안 돼서".
- A는 고민 단계의 "전송 방법 1(락을 잡은 채 전송)"과 같은 문제를 다시 만든다.
- 사용자 선택 근거 (B): "같은 세션끼리만 기다리면 돼서 다른 방은 안 막힌다". 깜빡할 위험은 "전송 메서드 하나로 사용 후 락 획득을 여기서 넣는다"로 줄인다.

## 결과와 트레이드오프

- 느린 소비자가 하나 있으면 그 방의 `SEND` 처리가 모두 느려지고, 기다리는 Tomcat 스레드가 쌓여 다른 방까지 영향을 줄 수 있다. P1-4에서는 받아들인다.
- 락은 세 종류가 되며 잡는 순서는 항상 **방 락 → (전체 락, 복사 동안만) → 세션 락**이다. 전체 락을 잡은 채 방 락이나 세션 락을 기다리는 경로, 세션 락을 잡은 채 방 락을 기다리는 경로가 없어야 교착이 생기지 않는다. 설계·구현에서 지킨다.
- 방 락 객체 (설계 단계에서 정함): 방 객체를 쓰면 방이 삭제·재생성될 때 두 스레드가 다른 락을 잡아 순서 ②가 드물게 깨지고, 방 객체를 얻으려면 맵 조회(전체 락)가 먼저 필요해 위 락 순서와 충돌한다(ADR-0008 대안 C의 재확인·재시도). 그래서 **방 이름의 해시로 고정 크기 락 배열의 칸을 고른다(락 스트라이핑)**. 같은 이름이면 항상 같은 락이고, 서로 다른 방이 같은 칸에 걸리면 기다림만 늘고 정확성은 유지된다. 두 방식의 열쇠 획득 비용은 EXP-02로 측정한다 (실행 전).
- P1-8에서 C(Decorator)를 쓰더라도 D는 버리지 않는다. Decorator는 세션 하나의 섞임과 느린 소비자만 다루고 멤버 사이의 순서는 보장하지 않는다. D 위에 얹으면 방 락 안에서는 각 세션 버퍼에 넣기만 해서 락을 짧게 잡는다.
- 문제 ②·④의 실제 증상(섞임 / 예외 / 순서 뒤바뀜)은 구현·검증 단계에서 방어 없는 구현으로 먼저 재현해 확인한다. 재현되지 않으면 이 ADR을 다시 본다.
- 문제 ② 재현 결과 (2026-10-24, `SessionSendConcurrencyTest`): 섞임이 아니라 Tomcat의 `IllegalStateException`(`TEXT_PARTIAL_WRITING`)으로 동시 쓰기가 거절되어 1,600번 중 1,475~1,564번이 유실됐다 (5회). 그동안 세션은 계속 open이었다 → "전송 실패만 보고 정리하지 않는다" 규칙의 근거가 실제로 확인됨. B 적용 후 5회 모두 유실 0.

## 재검토 조건

- 문제 ② 또는 ④가 방어 없는 구현에서 재현되지 않을 때 → 해당 결정이 필요한지 다시 판단한다.
- P1-8에서 느린 소비자가 재현될 때 → B를 C(Decorator, 후보)나 다른 대안과 비교해 바꾼다. 한도 값은 측정으로 정한다.
- P1-7 측정에서 방 락 대기가 병목으로 확인될 때 → E 등을 다시 검토한다.
