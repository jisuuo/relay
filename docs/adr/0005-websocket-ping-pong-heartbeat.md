# ADR-0005. 비정상 단절 감지: WebSocket ping/pong heartbeat

- 상태: Accepted
- 날짜: 2026-10-24
- 관련 Phase: P1 (P1-1, P1-5)

## 배경

P1-1에서 서버는 연결 시 세션을 저장소에 등록하고 종료 시 제거한다. 제거는 `afterConnectionClosed` 호출에 의존한다.

- 정상 종료: 클라이언트가 close frame을 보내므로 서버가 즉시 안다.
- 비정상 종료(네트워크 단절, 프로세스 강제 종료 등): close frame이 오지 않는다.

서버는 그 연결을 사용하려 할 때(`send`) 비로소 이상을 알 수 있지만, 두 가지 한계가 있다.

1. `send`는 OS 송신 버퍼에 쓰면 성공하므로, 상대 호스트가 사라진 경우 TCP 재전송이 포기될 때까지 수 분 이상 실패가 드러나지 않을 수 있다.
2. 방이 조용해 보낼 메시지가 없으면 끊긴 세션은 계속 남는다 (메모리 누수, 접속자 수 왜곡, 이후 브로드캐스트 실패).

따라서 보낼 메시지가 없어도 주기적으로 연결을 확인하는 heartbeat가 필요하다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. TCP keepalive | 애플리케이션 코드 불필요 | OS 기본값 기준 2시간 유휴 후 시작(설정에 따라 다름), 애플리케이션이 감지 시점을 통제하기 어려움 |
| **B. WebSocket ping/pong frame** | 표준 제어 frame, 클라이언트(브라우저 등)가 pong을 자동 응답하므로 클라이언트 코드 불필요 | ping 전송·pong 추적·타임아웃 종료는 서버가 직접 구현. 브라우저 JS는 ping 전송·pong 확인이 불가해 클라이언트 측 감지는 해결되지 않음 |
| C. 애플리케이션 메시지 (`{"type":"PING"}`) | 형식 자유, 양방향 감지 가능 | 클라이언트도 응답 로직 구현 필요, 메시지 모델에 제어용 타입이 섞임 |

## 결정

B. 서버가 주기적으로 WebSocket ping frame을 보내고, 타임아웃 안에 pong이 없는 세션을 닫아 저장소에서 제거한다.

주기와 타임아웃 값은 이 ADR에서 정하지 않는다. 설계·구현 단계에서 정하고 테스트로 확인한다. 시작 기준은 "주기 수십 초, 타임아웃은 주기의 2~3배"다.

## 근거

- 클라이언트 코드 없이 표준 동작(자동 pong)만으로 서버 측 감지가 가능하다.
- P1의 목표는 서버 측 세션 정리이므로, 클라이언트 측 감지가 안 되는 B의 한계는 현재 문제가 되지 않는다.
- A는 감지가 너무 늦고, C는 지금 필요하지 않은 클라이언트 구현 비용을 만든다.

## 결과와 트레이드오프

- 주기·타임아웃 트레이드오프: 짧으면 비용이 늘고 일시적 신호 약화를 단절로 오판할 수 있다. 길면 끊긴 세션이 오래 남고, 중간 프록시·로드밸런서의 유휴 타임아웃(예: Nginx 기본 60초)에 정상 연결이 끊길 수 있다.
- Raw WebSocket(ADR-0004)은 heartbeat를 자동 제공하지 않으므로 스케줄링과 세션별 pong 시각 추적을 직접 구현한다.

## 재검토 조건

- 클라이언트도 서버 단절을 감지해야 할 때 → C 검토
- 측정 결과 heartbeat 비용이 연결 수 대비 문제가 될 때 (P8)
