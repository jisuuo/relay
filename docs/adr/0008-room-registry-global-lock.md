# ADR-0008. 방 관리의 동시성: 전체 락 하나로 시작

- 상태: Accepted
- 날짜: 2026-10-24
- 관련 Phase: P1 (P1-3, P1-7)

## 배경

다중 방([ADR-0006](0006-multi-room-per-session.md))을 위해 서버는 방 → {세션들}, 세션 → {방들} 두 매핑을 가진다. P1-3 정의 단계에서 지켜야 할 불변식을 정했다.

1. S ∈ 방 A의 세션들 ⇔ A ∈ S의 방들
2. 빈 방은 존재하지 않는다
3. 끊긴 세션은 매핑에 없다

`JOIN`("방 찾기 → 추가")과 `LEAVE`·끊김("빈 방 확인 → 삭제")은 여러 단계로 된 동작이다. `ConcurrentHashMap`은 단계 하나하나만 안전하므로, 마지막 1명의 `LEAVE`가 빈 방을 지우기 직전에 다른 세션의 `JOIN`이 그 방 집합을 꺼내 쥐면 ①이 깨진다. T는 맵에서 떨어진 방에 들어가 이후 메시지를 받지 못한다. 예외는 없다 ([ISSUE-03](../phases/phase-01-websocket/issues/03-join-into-deleted-room.md)에서 재현).

## 검토한 대안

| 대안 | 경쟁을 막는가 | 대가 |
|---|---|---|
| A. 방마다 락 (방 찾기는 락 밖) | 아니오. 락을 기다리는 동안 방이 삭제되고, 락을 잡은 뒤 삭제된 방에 추가한다 | — |
| **B. 전체 락 하나** (방 찾기부터 두 매핑 갱신까지 락 안) | 예 | 서로 다른 방의 작업도 줄을 선다 |
| C. 방마다 락 + 락을 잡은 뒤 재확인 | 예. 확인 대상은 "방 A가 있는가"가 아니라 "맵의 방 A가 내가 쥔 바로 그 객체인가"이다 (그사이 같은 이름의 새 방이 생길 수 있음). 다르면 처음부터 다시 | 객체 비교·재시도·락 안 삭제 규칙을 모두 지켜야 한다 |

A는 P1-3 고민 단계에서 사용자가 처음 고른 방식이었고, 타임라인으로 따라가 같은 문제가 생김을 확인했다.

## 결정

B. `RoomRegistry`의 모든 메서드(`join`·`leave`·`removeSession`, 테스트용 스냅샷)를 `synchronized`로 감싼다. 모든 접근이 락 안에서 일어나므로 내부 맵은 `HashMap`·`HashSet`을 쓴다.

함께 정한 규칙:

- 없는 방에 `JOIN`하면 만든다 (방을 만드는 별도 메시지가 없다, [ADR-0007](0007-typed-client-message-model.md)).
- 이미 들어간 방에 다시 `JOIN`하면 아무 일도 없다 (멱등).
- 방에 없는 세션이 `LEAVE`하면 아무 일도 없이 `false`를 돌려준다. 클라이언트에 알리는 방법은 P1-5에서 정한다.
- 빈 방과, 방 목록이 빈 세션 항목은 모두 삭제한다.

## 근거

- 줄 서기가 실제 문제인지는 아직 재현되지 않았다. 재현된 문제가 있을 때만 복잡한 방법을 도입한다는 원칙([roadmap](../roadmap.md))에 따라 단순한 B에서 시작한다.
- 각 동작은 맵 몇 번 조회·수정으로 끝나 락을 잡는 시간이 짧다. 끊김 정리도 그 세션이 들어간 방 수만큼만 일한다.
- B는 방어 없는 구현에서 실패하던 경쟁 테스트를 통과시켰다 (ISSUE-03).

## 결과와 트레이드오프

- 서로 다른 방의 `JOIN`·`LEAVE`·끊김도 한 줄로 처리된다. 연결·입퇴장이 많을 때 락 대기가 처리량을 제한할 수 있다.
- P1-4 브로드캐스트에서 방의 세션 목록을 읽을 때도 같은 락 안에서 복사해야 한다. 전송 자체를 락 안에서 하면 느린 소비자 하나가 모든 방을 멈춘다.

- 대안 C와의 비교 측정 ([EXP-01](../phases/phase-01-websocket/experiments/01-room-lock-comparison.md), I/O 없는 반복 루프): C는 서로 다른 방에서 방이 유지되고 스레드가 많을 때만 빨랐다(64 스레드 약 3배). 같은 방 하나나 스레드 1개에서는 오히려 느렸다(0.64~0.87배). 또 C에서는 실행 도중 두 매핑의 일관된 모습을 볼 수 없었다.

## 재검토 조건

- P1-7 k6 측정이나 이후 측정에서 `RoomRegistry` 락 대기가 병목으로 확인될 때 → C(방마다 락 + 재확인)로 바꾸고 같은 경쟁 테스트로 검증한다. 사용자 결정: "전체 락 진행 후 문제 상황 발생 시 방마다 락 + 재확인으로".
