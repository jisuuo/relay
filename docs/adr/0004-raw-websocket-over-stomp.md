# ADR-0004. Phase 1 메시징 방식: Raw WebSocket으로 시작

- 상태: Accepted
- 날짜: 2026-10-24
- 관련 Phase: P1

## 배경

P1에서 클라이언트와 서버 사이의 실시간 양방향 통신을 구현한다. HTTP 요청/응답은 서버가 먼저 메시지를 보낼 수 없고, polling은 주기에 따라 부하(헛요청)와 지연 중 하나를 포기해야 하므로 WebSocket을 사용한다.

WebSocket은 연결 유지와 frame 전달만 제공한다. 채팅방을 만들려면 그 위에 다음이 필요하다.

1. 메시지 형식 (종류·목적지·내용 규칙)
2. 방 → 세션 매핑
3. 같은 방 세션들에 대한 브로드캐스트
4. 끊긴 세션을 매핑에서 정리

Spring에서는 이를 직접 구현하는 방식(`WebSocketHandler`)과 STOMP 지원(`@EnableWebSocketMessageBroker`)에 맡기는 방식 중 하나로 시작할 수 있다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| **A. Raw WebSocket (`WebSocketHandler`)** | 1~4의 동작과 실패 지점이 모두 코드에 드러나 문제를 직접 재현할 수 있음 | 메시지 규칙·라우팅을 직접 구현, 표준 클라이언트 라이브러리 없음, 직접 짠 코드의 버그도 떠안음 |
| B. STOMP + Simple Broker | 표준 프로토콜(`SUBSCRIBE`·`SEND`, destination), 클라이언트 라이브러리 존재, 1~4 대부분을 프레임워크가 처리 | 방 관리·브로드캐스트 내부가 가려짐. Simple Broker는 서버 메모리 안에서 동작하므로 다중 서버 문제는 A와 똑같이 남음 |
| C. STOMP + 외부 Broker Relay (RabbitMQ 등) | 서버 간 전달까지 해결하는 확장 경로 | P1은 단일 서버라 해결할 문제가 아직 없음. 외부 인프라가 추가됨 (도입 판단 기준 미충족) |

## 결정

A. Raw WebSocket(`WebSocketHandler`)으로 시작한다. 메시지 형식, 방 → 세션 매핑, 브로드캐스트, 끊긴 세션 정리는 애플리케이션 코드로 직접 구현한다.

## 근거

- 이 프로젝트의 목적은 "문제 발견 → 재현 → 해결"이다. 직접 만들어야 동시 수정, 끊긴 세션, 동시 전송, 느린 소비자 같은 문제를 실패하는 테스트로 재현할 수 있다.
- B가 해결해 주는 것(구현 비용 절감)은 P1 단계에서 학습 목표와 충돌한다. B의 확장 이점은 C로 가야 얻을 수 있는데, C는 아직 재현된 문제가 없다.

## 결과와 트레이드오프

- 메시지 형식을 JSON으로 직접 정의한다. 표준이 아니므로 클라이언트와의 약속을 문서와 테스트로 관리해야 한다.
- 이미 프레임워크가 해결한 문제(예: 세션 동시 전송 안전성)를 직접 만나게 된다. 이는 의도한 비용이다.
- 서버 간 전달은 해결하지 않는다. 방 → 세션 매핑은 서버 메모리에만 존재한다.

## 재검토 조건

- 서버가 여러 대가 되어 서버 간 메시지 전달 문제가 재현되면(P6 예상), Raw WebSocket 구조를 유지할지(Redis Pub/Sub, Kafka 등으로 서버 간 전달) STOMP + 외부 Broker로 바꿀지 다시 검토한다.
