# ADR-0006. 세션과 방의 관계: 한 세션이 여러 방에 참여

- 상태: Accepted
- 날짜: 2026-10-24
- 관련 Phase: P1 (P1-2, P1-3, P1-4)

## 배경

P1-1에서 연결(`/ws` 접속)과 세션 등록을 구현했다. P1-2에서 방 입장은 연결과 별개의 일이며 메시지(`JOIN`)로 요청한다고 정했다.

서버가 텍스트 frame을 받을 때 손에 쥔 것은 `WebSocketSession`(누가)과 메시지 문자열(무엇을)뿐이다. 따라서 "이 메시지를 어느 방에 보낼지"를 서버가 상태만으로 정할 수 있는지는, 한 세션이 동시에 몇 개의 방에 있을 수 있는지에 달려 있다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 1세션 = 최대 1방 | 서버가 세션 → 방(1:1)으로 대상 방을 알 수 있어 `LEAVE`·`SEND`에 `roomId` 불필요. 상태 구조 단순 | 이미 방에 있는 세션의 `JOIN` 처리 규칙(거절·자동 이동)이 필요. 연결 하나로 여러 방을 여는 클라이언트(PC 메신저 등)를 지원할 수 없음 |
| **B. 1세션 = 여러 방** | 연결 하나로 여러 방 참여 | 세션 → {방들}(1:N)이 되어 서버가 대상 방을 정할 수 없음 → `LEAVE`·`SEND`에도 `roomId` 필요. 방 → {세션들}과 세션 → {방들} 두 방향의 상태가 필요 |

## 결정

B. 한 세션이 여러 방에 동시에 참여할 수 있다. 모든 방 관련 메시지(`JOIN`·`LEAVE`·`SEND`)에 `roomId`를 담는다.

## 근거

- 다중 방 참여를 지원하고 싶다는 요구가 있다.
- 다중 방에서 "어느 방"은 클라이언트의 의도라서 클라이언트만 안다. 서버가 이미 확실히 아는 것(누가 = 세션)만 메시지에서 빼고, 클라이언트만 아는 것(어느 방에, 무엇을)은 메시지에 담는다는 원칙과 맞는다.
- 나중에 A에서 B로 바꾸면 메시지 형식(`roomId` 추가)과 상태 구조가 모두 바뀌므로, 되돌리기 어려운 결정이라 처음부터 B로 정한다.

## 결과와 트레이드오프

- `roomId`는 클라이언트가 마음대로 쓴 값이므로 서버는 그대로 믿지 않는다. `LEAVE`·`SEND`는 세션이 그 방의 멤버인지 서버 상태로 확인해야 한다 (P1-3·4).
- 연결이 끊기면 그 세션이 속한 **모든** 방에서 제거해야 한다. 이를 위해 세션 → {방들} 매핑을 둘지, 방 전체를 훑을지는 P1-3에서 정한다.
- 두 방향 매핑을 두면 둘을 함께 갱신할 때의 동시성 문제가 생긴다 (P1-3).

## 재검토 조건

- 측정 결과 두 방향 매핑의 유지 비용이 문제가 될 때 (P1-7, P8)
