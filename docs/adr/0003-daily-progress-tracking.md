# ADR-0003. 일일 진행 관리 방식

- 상태: Accepted
- 날짜: 2026-10-24
- 관련 Phase: 전체

## 배경

매일 이어서 진행하는 프로젝트다. 세션 시작 시 다음을 즉시 알 수 있어야 한다.

1. 어느 Phase·과제의 학습 루프 몇 단계까지 진행했는가
2. 오늘 할 다음 행동 하나
3. 직전에 무엇을 고민했는가 (열린 질문, 가설, 막힌 점)

git log는 "무엇을 바꿨는가"만 남기고 "어디까지 생각했는가"는 남기지 않는다. ADR-0001의 문서 구조에는 Phase 시작·완료 기록만 있고 그 사이의 진행 상태를 담을 곳이 없다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| A. 단일 진행 파일에 누적 | 단순함 | 비대해져 현재 위치를 찾기 어려움 |
| B. GitHub Issues·Projects | 시각적, 포트폴리오 효과 | 저장소 밖이라 세션 시작 시 자동으로 읽히지 않음, 관리 부담 |
| **C. 현재 위치 파일 + 일일 로그 분리** | 상태는 항상 짧고 이력은 날짜별 누적, 기존 docs 구조와 일관 | 파일 2종 관리 |

## 결정

C를 채택하고 다음 세 장치를 둔다.

### ① `docs/progress.md` — 현재 위치

항상 덮어쓰며 한 화면 분량을 유지한다. 현재 Phase·과제·단계, 다음 할 일, 열린 질문, Phase 과제 목록과 상태를 담는다.

### ② 과제별 5단계 체크리스트 — 각 Phase의 `plan.md` 안

마스터 프롬프트 4절의 11단계를 매일 체크 가능한 5단계로 묶는다.

| 단계 | 포함하는 원래 단계 |
|---|---|
| 1. 정의 | 1 문제·요구사항 정의, 2 현재 상태·예상 원인 분석 |
| 2. 고민 | 3 직접 고민(질문), 4 단계적 힌트, 5 장단점·위험 검토, 6 대안 비교 |
| 3. 설계 | 7 해결 방법 선택·최소 설계 |
| 4. 구현·검증 | 8 구현, 9 테스트로 예상 vs 실제 비교 |
| 5. 정리 | 10 결과 분석·개선, 11 문서화 |

```markdown
### P1-1 <과제명>
- [ ] 1. 정의: 요구사항 정리, 문제 찾기 질문 6개로 내가 문제 문장 작성
- [ ] 2. 고민: 원인·해결책 직접 고민, 힌트, 대안 비교 → (필요 시) ADR
- [ ] 3. 설계: 최소 설계와 테스트 시나리오 확정
- [ ] 4. 구현·검증: 실패하는 테스트 → 구현 → 통과, 예상 vs 실제 비교
- [ ] 5. 정리: 결과 분석, 회고 기록
```

2단계(고민)는 사용자가 자신의 답을 낸 뒤에만 체크한다. 고민을 건너뛰고 구현으로 넘어가는 것을 막기 위함이다.

1단계(정의)도 같은 원칙을 따른다. 사용자가 [문제 찾기 질문 6개](../learning/problem-finding-questions.md)로 문제 문장을 직접 적은 뒤에만 체크한다 (아래 보완 2026-10-24 ②).

### ③ `docs/journal/YYYY-MM-DD.md` — 일일 로그

작업한 날만 5줄 내외로 작성한다.

```markdown
# YYYY-MM-DD
- 한 일:
- 배운 것:
- 막힌 것 / 질문:
- 다음:
```

### 세션 흐름

| 시점 | 작업 |
|---|---|
| 세션 시작 | Claude가 `progress.md`와 최근 journal을 읽고 현재 위치, 오늘 할 일 1개, 이어갈 질문을 요약 |
| 작업 중 | `plan.md` 체크리스트 갱신, 필요 시 ADR·변경 기록 |
| 세션 종료 ("오늘 마무리") | journal 작성, `progress.md` 갱신, `docs:` 커밋과 push |

## 근거

- 현재 위치와 이력을 분리하면 세션 시작 시 읽을 분량이 일정하게 유지된다.
- 저장소 안 파일이므로 Claude가 CLAUDE.md 규칙만으로 매 세션 읽을 수 있다. hook 자동화는 필요가 확인되면 도입한다.

## 결과와 트레이드오프

- 세션 종료 시 기록 비용이 생긴다. journal을 5줄 내외로 제한해 부담을 줄인다.
- journal의 "배운 것"은 사용자의 학습 내용이므로 Claude가 임의로 채우지 않고 사용자 표현을 기록한다.

## 보완 (2026-10-24): SessionStart hook 도입

사용자 요청("시작하면 알아서 다음 단계를 가져오면 좋겠다")으로 CLAUDE.md 규칙만으로는 부족함이 확인되어 hook을 추가한다. 결정의 방향은 같고 실행 수단만 보강하는 것이므로 새 ADR 대신 이 절에 기록한다.

- `.claude/settings.json`의 SessionStart hook(`startup|resume|clear`)이 `.claude/hooks/session-brief.sh`를 실행한다.
- 스크립트는 `progress.md`의 "현재 위치", "다음 할 일" 섹션을 사용자 화면에 표시하고(`systemMessage`), `progress.md` 전체와 최신 journal을 Claude 컨텍스트에 주입한다(`additionalContext`).
- 한계: Claude는 사용자 메시지 없이 먼저 말할 수 없다. 화면 표시는 즉시 되지만, Claude의 상세 브리핑(다음 단계 구체화)은 사용자의 첫 메시지(예: "시작") 이후에 나온다.

## 보완 (2026-10-24) ②: 1단계(정의)에 문제 찾기 질문 도입

P1-3 정의 중 사용자 요청("저렇게 내가 정의해볼 수 있도록 단계에 넣어주세요")으로 추가한다. 품질속성과 문제를 Claude가 먼저 나열하면 사용자가 정의를 스스로 해 볼 기회가 없어진다. 5단계 구조는 그대로 두고 1단계의 실행 방법만 구체화하는 것이므로, 새 ADR 대신 이 절에 기록한다.

- 1단계에서 사용자가 [문제 찾기 질문 6개](../learning/problem-finding-questions.md)(불변식 / 동시 접근 / 넣고 빼기 짝 / 비용 증가 / 확인 방법 / 범위)를 과제에 적용하고, 찾은 문제를 "[사건]이 [조건]에서 일어나면 [불변식/자원]이 깨진다 → 결과: [증상]" 문장으로 적는다.
- Claude는 질문을 하나씩 던지고, 사용자가 답한 뒤 빠진 것을 반례로 보충한다. 답을 먼저 나열하지 않는다.
- 적용 범위: P1-3부터. 이미 완료한 P1-1·P1-2 체크리스트 문구는 바꾸지 않는다.

## 재검토 조건

- `progress.md`가 한 화면을 넘어 비대해질 때
- 체크리스트 5단계가 실제 진행과 반복적으로 맞지 않을 때
- 진행 현황을 외부(포트폴리오 등)에 보여줄 필요가 생길 때 → GitHub Projects 재검토
