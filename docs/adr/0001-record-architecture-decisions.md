# ADR-0001. 문서화 방식과 ADR 작성 기준

- 상태: Accepted
- 날짜: 2026-10-24
- 관련 Phase: 전체

## 배경

이 프로젝트의 목표는 기능 구현이 아니라 "문제 발견 → 원인 분석 → 해결책 비교 → 구현 → 검증"의 과정을 설명할 수 있게 되는 것이다.
결정의 이유와 계획 변경 이력이 남지 않으면 회고(P10) 시점에 근거를 재구성할 수 없다.

## 검토한 대안

| 대안 | 장점 | 단점 |
|---|---|---|
| 단일 문서에 모두 기록 | 단순함 | 결정·변경·Phase 기록이 섞여 검색과 추적이 어려움 |
| Phase 문서 안에만 결정 기록 | Phase 맥락과 함께 보임 | Phase를 가로지르는 결정(ID 체계 등)의 위치가 모호함 |
| Phase·ADR·변경 기록 분리 | 목적별 추적 용이, 결정 번복 이력 관리 가능 | 문서 수 증가, 색인 관리 필요 |

## 결정

`docs/` 아래를 다음과 같이 분리한다.

- `phases/phase-XX-<slug>/plan.md`: Phase 시작 시 작성. 승인 후 구현 시작.
- `phases/phase-XX-<slug>/review.md`: Phase 완료 시 작성.
- `phases/phase-XX-<slug>/experiments/`: 측정·장애 재현 결과가 실제로 생길 때만 생성.
- `adr/NNNN-<slug>.md`: 기술적 의사결정.
- `changes/NNN-<slug>.md`: 계획 대비 변경.

### ADR과 변경 기록의 구분

| 구분 | `adr/` | `changes/` |
|---|---|---|
| 질문 | 무엇을, 왜 선택했는가? | 계획과 무엇이 달라졌는가? |
| 대상 | 기술·설계·아키텍처 선택 | Phase 순서·범위·완료 기준 변경 |
| 수명 | 번복 시 새 ADR로 대체(Superseded) | 작성 후 수정하지 않음, `roadmap.md`에 반영 |

둘 다 해당하면 ADR을 본문으로 작성하고, 변경 기록에는 요약과 ADR 링크만 남긴다.

### ADR 작성 기준 (하나라도 해당 시)

- 대안을 2개 이상 비교했다.
- 되돌리기 어렵다 (스키마, 프로토콜, ID 체계 등).
- 학습 후보 기술을 도입하지 않거나 대체하기로 했다.

사소한 선택(라이브러리 패치 버전 등)은 ADR로 작성하지 않는다.

### 작성 절차

| 시점 | 작업 | 커밋 메시지 예 |
|---|---|---|
| Phase 시작 | `plan.md` 작성 후 승인 | `docs: phase-XX 계획 작성` |
| 기술 선택 | ADR `Proposed` 작성 → 결정 후 `Accepted` | `docs(adr): ADR-NNNN ...` |
| 계획 변경 | `changes/` 기록과 `roadmap.md` 갱신을 같은 커밋에 | `docs(changes): CHG-NNN ...` |
| Phase 완료 | `review.md`, `plan.md` 상태, `docs/README.md` 색인 갱신 | `docs: phase-XX 회고` |

문서 커밋과 코드 커밋은 분리한다. 테스트 결과는 실제로 실행한 내용만 기록한다.

### 템플릿

**plan.md**

```markdown
# Phase XX. <이름> — 계획
- 상태: 진행 중 | 완료
- 시작일: YYYY-MM-DD
- 선행 Phase:

## 학습 목표
## 문제 정의
## 범위 / 비범위
## 원인 가설
## 검토할 해결 방법
## 테스트 시나리오
## 완료 기준
## 관련 ADR / 변경 기록
```

**review.md**

```markdown
# Phase XX. <이름> — 회고
- 완료일: YYYY-MM-DD

## 구현 내용과 주요 코드의 역할
## 테스트 결과
## 성능 측정 결과
## 발생한 문제와 해결
## 완료 기준 점검표
## 한계와 후속 과제
```

**ADR**

```markdown
# ADR-NNNN. <결정 제목>
- 상태: Proposed | Accepted | Superseded by ADR-XXXX | Deprecated
- 날짜: YYYY-MM-DD
- 관련 Phase:

## 배경
## 검토한 대안
## 결정
## 근거
## 결과와 트레이드오프
## 재검토 조건
```

**변경 기록**

```markdown
# CHG-NNN. <변경 제목>
- 날짜: YYYY-MM-DD
- 영향 Phase:

## 기존 계획
## 변경 내용
## 변경 이유
## 영향
## 관련 ADR
```

## 근거

결정·변경·진행 기록을 분리하면 P10 회고에서 "어떤 문제가 있었고 왜 그렇게 선택했는가"를 문서 링크만으로 추적할 수 있다.

## 결과와 트레이드오프

- 문서 수와 색인(`docs/README.md`, `adr/README.md`, `changes/README.md`) 관리 비용이 생긴다.
- 기록 누락을 막기 위해 Phase 완료 점검 시 색인 갱신 여부를 확인한다.

## 재검토 조건

- 문서 관리 비용이 학습 진행을 눈에 띄게 방해할 때
- ADR과 변경 기록의 구분이 반복적으로 모호할 때
